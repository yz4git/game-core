# Large Batch 38 — Schema Evolution and Mixed-Version Replay Compatibility

Date: 2026-09-24

## Scope
Coverage review showed protocol admission/version cohorts are already well covered, while schema evolution and long-lived replay compatibility remain high-priority. This batch therefore focuses on how network/replay data survives additive/removal changes, custom serializers, asset/ruleset drift, and archival playback. Historical context is cross-checked against Gaming Alexandria holdings rather than copied: PC Engine Fan complete run, Gekkan PC Engine 1988–1994, Play Meter holdings spanning the 1970s–1990s, and the broader magazine archive/sets. These sources are useful as a long-duration reminder that software ecosystems, media, add-ons, strategy knowledge and platform generations outlive any one executable build.

Modern comparison set: Unreal Engine Replay backward compatibility and HTTP replay version filtering; Photon Quantum deterministic replay requirements/checksums; Protocol Buffers schema-evolution guidance; historical Unity network serialization/RPC documentation as a contrast case. No magazine body text, scans, images, long quotations, or close paraphrases are stored here.

## New observations → mechanisms → principles → transfers → playtest questions

### 1. Replay compatibility is a reader contract, not a build-number equality test
**Observation:** Mature replay systems can read selected older formats even when the executable changed.
**Mechanism:** The reader knows the recorded network/game version and conditionally maps old fields into current runtime state.
**Generalized Principle:** Define a supported read-compatibility window independently from live-session join compatibility.
**Transfer:** Store replay format epoch, game/network version and schema fingerprint in every replay envelope.
**Playtest Question:** Can the current build read every replay epoch it claims to support, and reject the rest before partial playback?

### 2. Additive/removal changes are safer than semantic reuse
**Observation:** Systems can often skip removed fields and default newly added fields, but this does not make arbitrary field reuse safe.
**Mechanism:** Stable field identity lets readers distinguish unknown/absent data; reused identity silently changes meaning.
**Generalized Principle:** Preserve wire identity forever within an epoch; retire IDs instead of recycling them.
**Transfer:** Maintain reserved/tombstoned field/RPC/component IDs and lint reuse in CI.
**Playtest Question:** Does an old fixture ever deserialize a newly reused ID into a plausible but wrong value?

### 3. Custom serializers are explicit migration boundaries
**Observation:** Engine-provided compatibility can handle ordinary replicated fields while custom serialization requires manual handling.
**Mechanism:** Custom byte layouts bypass generic field-aware migration logic.
**Generalized Principle:** Every custom serializer owns a versioned reader matrix and golden fixtures.
**Transfer:** Prefix custom payloads with format version and keep readers for the declared support horizon.
**Playtest Question:** Is every custom NetSerialize/binary blob represented by at least one old-version fixture?

### 4. Deterministic input replay depends on executable semantics, not only input bytes
**Observation:** Deterministic replay frameworks require matching simulation libraries/assets/configuration and may verify checksums.
**Mechanism:** The same input stream diverges if physics, RNG order, data tables or simulation code changes.
**Generalized Principle:** Input-only replay is a dependency bundle, not a self-sufficient historical record.
**Transfer:** Record simulation build/content fingerprints and periodic checksums; retain compatible runtime/data or provide transcoding.
**Playtest Question:** At which tick does an old input replay first diverge under the new build, and which dependency changed?

### 5. Replay browsing needs compatibility metadata before download/playback
**Observation:** Replay services can filter by application/build/network version.
**Mechanism:** Compatibility metadata is queryable without attempting full playback.
**Generalized Principle:** Make replay compatibility discoverable at catalog time, not only after loading megabytes of data.
**Transfer:** Index replay epoch, required capabilities, content/ruleset IDs and reader status in metadata.
**Playtest Question:** Can UI distinguish playable, migratable, archive-only and unsupported recordings before selection?

### 6. Live protocol compatibility and replay compatibility are different graphs
**Observation:** A build may be unsafe to join live with an older peer yet perfectly able to read that peer's historical recording.
**Mechanism:** Live play is bidirectional and authoritative; replay is usually one-way interpretation.
**Generalized Principle:** Track `canJoin` and `canReadReplay` separately and directionally.
**Transfer:** Generate pairwise compatibility matrices for live, replay, spectator and migration paths.
**Playtest Question:** Are releases being rejected from replay unnecessarily because live protocol epochs differ?

### 7. Semantic migrations need invariants after syntactic decode
**Observation:** Successful deserialization proves byte/schema compatibility, not gameplay correctness.
**Mechanism:** Renamed states, changed enum meaning, new quest/rules constraints or altered asset references can decode while becoming nonsensical.
**Generalized Principle:** Replay/schema migration ends with semantic validation, not parser success.
**Transfer:** Validate entity references, state-machine legality, ownership, ranges and ruleset invariants after conversion.
**Playtest Question:** Can a migrated replay parse cleanly yet create impossible gameplay state?

### 8. Snapshot checkpoints reduce long-chain migration risk
**Observation:** Replaying a long history through many schema generations compounds migration and determinism risk.
**Mechanism:** Periodic canonical snapshots bound how much old event/input history must be interpreted.
**Generalized Principle:** Bound historical reconstruction depth with versioned checkpoints.
**Transfer:** Store periodic snapshots plus subsequent event/input tail; migrate snapshot and tail independently.
**Playtest Question:** What is the maximum historical chain a current reader must reconstruct before reaching a canonical checkpoint?

### 9. Transcoding should be transactional and provenance-preserving
**Observation:** Converting old recordings can make archives usable but can also erase evidence of what was original.
**Mechanism:** In-place replacement loses source bytes and conversion lineage.
**Generalized Principle:** Never make migration destroy the archival source.
**Transfer:** Produce a new artifact with source hash, converter version, target epoch and validation result; retain original immutable recording.
**Playtest Question:** Can a bug in today's converter be corrected later from the untouched source?

### 10. Capability absence needs explicit playback degradation
**Observation:** Old recordings may reference camera modes, UI events, cosmetics or telemetry no longer implemented.
**Mechanism:** Treating every missing optional feature as fatal unnecessarily shortens archive life; silently ignoring required simulation data corrupts meaning.
**Generalized Principle:** Classify replay dependencies as simulation-critical, interpretation-critical, presentation-optional or metadata-only.
**Transfer:** Allow explicit degraded playback only when missing capabilities cannot alter canonical outcome.
**Playtest Question:** Does degraded mode clearly identify what is omitted, and can it ever omit outcome-affecting data?

### 11. Replay fixtures are executable historical documentation
**Observation:** Written compatibility promises drift; old artifacts reveal the actual contract.
**Mechanism:** Golden recordings exercise serializer, rules, assets, migration and playback together.
**Generalized Principle:** Preserve a small corpus per shipped epoch as part of release engineering.
**Transfer:** Keep boundary cases, long sessions, reconnect/host migration, custom serializer, rare entities and content-version cases.
**Playtest Question:** Does CI run the oldest supported fixture as well as N-1?

### 12. Retirement needs evidence, not age alone
**Observation:** Supporting every historical format forever has cost, while deleting readers blindly destroys player/community history.
**Mechanism:** Reader code, assets and fixtures impose maintenance/storage/security burden; usage varies by title/community.
**Generalized Principle:** Retire compatibility using measured demand, security risk, migration success and archival alternatives.
**Transfer:** Telemetry should count read attempts by epoch without storing unnecessary player identity; offer export/transcode before removal.
**Playtest Question:** Before retiring an epoch, what fraction of active replay views would fail and is a validated migration path available?

## Implementation model

Replay envelope should minimally carry:
`replayId, sourceBuildId, replayEpoch, networkVersion, rulesetId, contentId, schemaFingerprint, simulationFingerprint, requiredCapabilities, optionalCapabilities, checksumScheme`.

Reader pipeline:
`CATALOG FILTER → ENVELOPE VERIFY → READER SELECTION → DEPENDENCY CHECK → DECODE → VERSIONED MIGRATION → SEMANTIC VALIDATION → CHECKSUM/DIVERGENCE CHECK → PLAYABLE | DEGRADED | MIGRATABLE | UNSUPPORTED`.

CI matrix should include current/current, every advertised old→current reader path, custom serializer boundaries, removed/additive fields, unknown optional fields, changed enums, content drift, deterministic divergence, truncated/corrupt data, and transcode round-trip/provenance checks.

## Promotion candidates
- Compatibility is directional and surface-specific: live join, replay read, spectator read, host, reconnect are separate contracts.
- Stable serialized identity must not be recycled; removal creates a tombstone/reservation.
- Custom serializers are explicit migration boundaries requiring versioned readers and fixtures.
- Input-only deterministic replay requires simulation/content provenance plus divergence checks.
- Compatibility fixtures are executable historical documentation and should survive for the advertised support horizon.
