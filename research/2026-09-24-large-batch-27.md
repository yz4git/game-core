## Observation → Mechanism → Generalized Principle → Transfer → Playtest Question

### 1. Rollback cost is multiplicative, not a normal-frame surcharge
**Observation:** Rollback restores an earlier state and can execute several simulation ticks before the next presentation frame.
**Mechanism:** A transient late-input event concentrates multiple simulation steps into one display deadline.
**Generalized Principle:** Budget rollback by **worst credible re-simulation burst**, not average simulation cost.
**Transfer:** Record normal tick p95, rollback tick p95, maximum ticks replayed per render frame, and total catch-up time.
**Playtest Question:** Can a common rollback depth be re-simulated without missing the next visible frame on the slowest supported phone?

### 2. Headroom is part of netcode quality
**Observation:** A game that consumes nearly the entire frame budget offline has no room for rollback bursts, packet processing, GC, or browser work.
**Mechanism:** Network correction competes with rendering and JavaScript runtime work for the same deadline.
**Generalized Principle:** Offline 60 fps is not sufficient evidence of rollback readiness; reserve explicit CPU headroom.
**Transfer:** Set a simulation+network budget below the full 16.67 ms frame and treat remaining time as resilience reserve.
**Playtest Question:** What happens to input-to-present latency when a rollback burst coincides with a heavy render frame?

### 3. Snapshot history is a memory product: state size × history depth
**Observation:** Rollback needs prior states; deeper rollback and larger worlds increase retained memory.
**Mechanism:** Even compact per-frame growth becomes material when multiplied by players, entities, history frames and temporary copies.
**Generalized Principle:** Track **bytes per rollback frame** as a first-class performance metric.
**Transfer:** Measure serialized authoritative-state bytes, ring-buffer capacity, peak temporary restore allocation and history high-water mark.
**Playtest Question:** Does memory remain bounded after repeated deep rollbacks rather than only during a clean match?

### 4. Hot-path allocation converts rollback into GC risk
**Observation:** WebKit performance work treats garbage-collection pauses as part of real workload performance, not an isolated VM detail.
**Mechanism:** Re-simulation multiplies allocation-heavy code and can trigger GC exactly when catch-up needs spare CPU.
**Generalized Principle:** Rollback simulation should be allocation-stable after warm-up.
**Transfer:** Reuse snapshot buffers, event arrays and entity scratch storage; log allocation proxies/high-water marks around rollback bursts.
**Playtest Question:** Do frame spikes correlate with rollback depth only, or with allocation/GC behavior at particular depths?

### 5. Simulation cost and render cost must be independently degradable
**Observation:** GGPO requires running restored gameplay frames without rendering every intermediate frame.
**Mechanism:** Catch-up needs authoritative simulation results, not repeated visual composition.
**Generalized Principle:** Rendering, particles, camera, audio and haptics must not be prerequisites for advancing simulation.
**Transfer:** Provide a `simulateTick(render=false)` or equivalent architecture and benchmark catch-up with presentation suppressed.
**Playtest Question:** Can eight simulation ticks execute cheaper than eight complete rendered frames by a large margin?

### 6. Refresh rate is not simulation rate
**Observation:** `requestAnimationFrame()` generally follows display refresh rate and can therefore run at 60, 120 Hz or other rates.
**Mechanism:** Binding one simulation tick to one rAF callback changes game speed/cost across displays.
**Generalized Principle:** Use an explicit fixed simulation clock; treat display callbacks as presentation opportunities.
**Transfer:** Cap accumulated catch-up work per presentation and interpolate presentation when appropriate.
**Playtest Question:** Does gameplay remain deterministic and same-speed on 60 Hz and high-refresh displays?

### 7. Backgrounding is a discontinuity, not a giant slow frame
**Observation:** Browsers commonly pause `requestAnimationFrame()` and throttle timers for hidden pages.
**Mechanism:** On resume, wall-clock elapsed time can be seconds or minutes while no simulation frames were delivered.
**Generalized Principle:** Never feed background elapsed time into normal fixed-step catch-up.
**Transfer:** On `visibilitychange`, freeze local presentation/simulation policy and resume through network resynchronization/snapshot logic.
**Playtest Question:** After 30 seconds backgrounded, does resume request authoritative state rather than trying to simulate thousands of missed ticks?

### 8. Resume belongs to the reconnect state machine
**Observation:** Browser visibility lifecycle and network connection lifecycle can change together on mobile.
**Mechanism:** A page may return visible with stale sockets, stale authority and stale local history.
**Generalized Principle:** Treat resume as a possible **authority invalidation boundary**.
**Transfer:** VISIBLE → VERIFY SESSION → SNAPSHOT/DELTA → CATCHUP → READY when uncertainty exists.
**Playtest Question:** Can the player act on stale world state for even one frame after returning from background?

### 9. Performance instrumentation must have graceful capability fallbacks
**Observation:** PerformanceObserver is broadly useful, while specific entry types and Device Memory support vary across browsers.
**Mechanism:** Depending on one optional telemetry API creates blind spots precisely on unsupported devices.
**Generalized Principle:** Instrumentation should be capability-detected and layered.
**Transfer:** Always collect app-level tick/frame timings; add supported browser performance entries opportunistically; never gate correctness on `deviceMemory`.
**Playtest Question:** Does the QA build still produce actionable rollback telemetry when optional browser APIs are absent?

### 10. Long-frame telemetry should be correlated with rollback events
**Observation:** Long Animation Frame tooling identifies rendering updates delayed beyond 50 ms and can expose blocking contributors where supported.
**Mechanism:** A generic long-frame count cannot distinguish rollback cost from unrelated UI/render/script spikes.
**Generalized Principle:** Timestamp network correction events into the same performance timeline as frame stalls.
**Transfer:** Mark rollback start/end, depth, restore time, re-sim time and presentation correction; correlate with top-N long frames.
**Playtest Question:** What fraction of the worst frame stalls occur within rollback windows?

### 11. Thermal degradation requires sustained tests, not launch benchmarks
**Observation:** Apple explicitly connects web CPU usage with energy efficiency; sustained high CPU work affects the practical mobile performance envelope.
**Mechanism:** A configuration that passes a short cold-device benchmark can lose headroom during a long session.
**Generalized Principle:** Mobile rollback budgets need **sustained-performance acceptance tests**.
**Transfer:** Run 20–30 minute network fault traces and compare first-five-minute versus final-five-minute frame/rollback distributions.
**Playtest Question:** Does max safe rollback depth shrink after sustained play?

### 12. Adaptive quality should shed presentation before game truth
**Observation:** Rollback requires deterministic simulation correctness, while visual work can often be reduced independently.
**Mechanism:** Lowering authoritative simulation fidelity under load risks divergence; reducing cosmetic cost preserves rules.
**Generalized Principle:** Degradation ladder: cosmetic density → render resolution/DPR → expensive post effects → remote visual interpolation detail, while authoritative tick rules remain stable.
**Transfer:** Define explicit quality tiers activated by sustained budget pressure, not a one-frame spike.
**Playtest Question:** Can the game recover CPU/GPU headroom without changing collision, AI, RNG or command timing?

### 13. Rollback depth should have a platform budget, not only a network maximum
**Observation:** A theoretically supported rollback window may be too expensive to execute inside a mobile frame deadline.
**Mechanism:** Network tolerance and compute tolerance are separate constraints.
**Generalized Principle:** `maxRollbackFrames = min(network-policy limit, compute-safe limit, memory-safe limit)`.
**Transfer:** Benchmark safe depths per device/performance tier and choose delay/recovery policy when the required depth exceeds the safe compute envelope.
**Playtest Question:** At what depth does correction remain logically possible but no longer presentation-safe?

### 14. Production telemetry should describe the budget envelope, not identify the device owner
**Observation:** Device-memory signals can be coarse and privacy-limited; exact hardware identity is not necessary for most performance decisions.
**Mechanism:** Frame timing, rollback depth and memory high-water behavior directly describe whether the workload fits.
**Generalized Principle:** Prefer workload telemetry over fingerprint-like hardware classification.
**Transfer:** Aggregate anonymous performance tier, frame-time histograms and rollback metrics; avoid collecting unnecessary device identifiers.
**Playtest Question:** Can every performance decision be made from workload measurements without storing a uniquely identifying hardware profile?

## Proposed mobile rollback budget sheet

For each supported performance tier, record:

- target simulation Hz
- target presentation Hz
- normal simulation tick p50/p95/p99
- render p95/p99
- network processing p95
- snapshot save/load p95
- bytes per saved state
- rollback history high-water bytes
- rollback depth p50/p95/max
- re-simulation burst p95/max
- rollback-window missed-frame rate
- input-to-present p95
- longest frame top-N
- 5-minute versus 30-minute sustained delta
- background/resume recovery time
- reconnect-to-READY p95

## Suggested acceptance gates

Do not hard-code universal millisecond limits from desktop data. Establish gates empirically on the slowest supported iPhone class. Useful invariant-style gates are:

1. No unbounded growth in rollback history or temporary buffers.
2. No authoritative simulation rule changes under adaptive quality.
3. No normal fixed-step catch-up from long background intervals.
4. No stale actionable frame after uncertain resume.
5. Common rollback depth fits inside reserved headroom at sustained temperature.
6. Worst rollback depth has a defined fallback rather than an uncontrolled spiral.
7. QA artifacts can identify restore, re-simulation, render and GC-like stalls separately.

## Promotion candidates

- Performance headroom is resilience capacity, not wasted capacity.
- Background/resume is a state discontinuity and should not be treated as elapsed simulation time.
- Degrade presentation before authoritative simulation.
- Network rollback limits must also obey compute and memory limits.
- Measure workload behavior directly rather than relying on hardware identity heuristics.
