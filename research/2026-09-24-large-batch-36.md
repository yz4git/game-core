# Large Batch 36 — Cross-origin save portability and deployment-origin migration

Date: 2026-09-24

## Why this batch

`research/COVERAGE.md` listed cross-origin / deployment-origin migration and save portability as a high-priority gap. Batch 28 covered browser quota/eviction and Batch 29–30 covered content compatibility and divergent branches, but none answered a common web-game failure: a deployment moves from one origin to another and a perfectly valid local save becomes invisible because browser storage is origin-scoped.

This batch treats origin changes as a save migration event, not as a hosting detail.

## Material sampled

Historical / preservation cross-sample:

- Program Pochette ’84 Vol. 1 preserved programs (Alien, Doodle-saurus, The UFO) — early software where load/restart/media procedures were part of the usable game artifact.

- Famimaga 64 Issue 12 (1996), Issue 1 appendix, and complete 1996–1998 run — platform transition and preserved companion material.
- Dengeki PC Engine / Dengeki G’s Engine complete-run history — publication/platform identity transition across 1993–1997.

Modern technical material:
- MDN Same-origin policy: Web Storage and IndexedDB are isolated by origin (scheme/host/port).
- MDN Web Storage: `localStorage` is origin-scoped and persists across browser sessions.
- WebKit Storage Policy / Safari 17 Storage API: quota and eviction are origin based; standalone Home Screen web apps use origin storage policy.
- MDN Storage Access API: cross-site embedded access is permission- and context-constrained, not a general-purpose first-party save transfer mechanism.
- OWASP HTML5 Security: browser-local storage must not be treated as authenticated/trusted storage for sensitive authority.

No magazine prose, scans, images, or long/near quotations are stored here. Historical material is used only as broad design/preservation context; the mechanisms below are independently generalized.

## New observations / mechanisms

### 1. A deployment URL can be part of the persistence ABI
**Observation:** Browser-local state that survives ordinary updates can become unreachable when scheme, host, or port changes.

**Mechanism:** Web Storage and IndexedDB are separated by origin. A new origin receives a different storage namespace even if the game code, account and save schema are identical.

**Generalized Principle:** Treat origin identity as part of the persistence ABI. Changing origin is a migration event.

**Transfer:** GitHub Pages → custom domain, staging → production, HTTP → HTTPS, project subdomain changes, hosting-provider moves.

**Playtest Question:** If the production origin changes today, can a returning player recover without manually understanding browser storage?

### 2. Schema compatibility and storage reachability are orthogonal
**Observation:** A save can be fully compatible yet inaccessible to the new build.

**Mechanism:** Migration code only helps after bytes have been obtained; same-origin isolation can prevent the new deployment from reading the old store at all.

**Generalized Principle:** Preflight persistence in two phases: `LOCATE/ACQUIRE` first, `PARSE/MIGRATE/VALIDATE` second.

**Transfer:** Web saves, PWA upgrades, launcher/profile migrations, console-account transfers.

**Playtest Question:** Does diagnostics distinguish “no save exists” from “save may exist at a previous location we cannot directly read”?

### 3. Redirects move navigation, not local storage
**Observation:** Redirecting an old game URL to a new host does not carry IndexedDB/localStorage with it.

**Mechanism:** Navigation changes the active origin; it does not merge origin-scoped storage namespaces.

**Generalized Principle:** Never use an HTTP redirect alone as a save migration plan.

**Transfer:** Domain consolidation, renamed GitHub Pages repositories, CDN migrations.

**Playtest Question:** Has the migration path been tested with a real old-origin save rather than only a redirected URL?

### 4. The old origin is a migration endpoint while it still exists
**Observation:** Only code executing with access to the old origin can normally read its first-party browser state.

**Mechanism:** Same-origin isolation makes the old deployment uniquely capable of exporting its local save without privileged browser behavior.

**Generalized Principle:** Preserve a minimal old-origin migration shell for a defined compatibility horizon.

**Transfer:** A tiny page can read old save generations, validate identity/version, create a portable package, and guide the user to the new origin.

**Playtest Question:** Is the old origin retired only after migration adoption and recoverable-save risk fall below an explicit threshold?

### 5. Cross-origin handoff should move a portable artifact, not grant ambient storage access
**Observation:** Browser APIs that relax embedded storage restrictions are permission/privacy mechanisms with context-specific constraints.

**Mechanism:** Storage Access API behavior depends on embedding, user activation, browser policy and partitioning; it is not equivalent to letting a new first-party origin browse another origin’s IndexedDB.

**Generalized Principle:** Prefer explicit export/import or authenticated server handoff over hidden cross-origin storage coupling.

**Transfer:** One-time migration token, downloaded JSON/package, account-backed cloud transfer.

**Playtest Question:** Does migration still work when third-party storage is blocked and no iframe exception is granted?

### 6. Portable saves need identity and integrity envelopes
**Observation:** Once a save leaves its original storage namespace, it loses implicit context about where it came from.

**Mechanism:** Importing arbitrary local bytes can confuse profile/world identity, replay stale revisions, or allow tampering to cross trust boundaries.

**Generalized Principle:** A portable save envelope should declare `formatVersion`, `gameId`, `saveUUID`, `profile/world identity`, `revision`, `createdAt`, `sourceOrigin`, content compatibility metadata, and integrity/authenticity information appropriate to the game's trust model.

**Transfer:** Manual export, QR/device transfer, cloud restore, support recovery packages.

**Playtest Question:** Can a valid save for another profile/world be rejected before replacing local progress?

### 7. Import must be staged and non-destructive
**Observation:** A migration can fail after the source has already been exported successfully.

**Mechanism:** New-origin quota, schema migration, content dependency, identity mismatch, or semantic validation may fail at destination.

**Generalized Principle:** `ACQUIRE → STAGE → VERIFY → MIGRATE → SEMANTIC VALIDATE → COMMIT`; never delete source or overwrite the only destination known-good generation before commit.

**Transfer:** Browser origin moves and ordinary cross-device import share the same transactional pipeline.

**Playtest Question:** What remains recoverable if the tab closes at every boundary in the import pipeline?

### 8. Migration tokens should be single-purpose capabilities
**Observation:** A server-assisted transfer can accidentally become a durable bearer credential.

**Mechanism:** Long-lived reusable URLs/tokens may expose save data through history, logs, screenshots, referrers, or replay.

**Generalized Principle:** Use short-lived, one-time, narrowly scoped migration capabilities; bind them to intended game/profile/save revision where possible and invalidate after successful claim.

**Transfer:** Accountless browser-game migration and device-link flows.

**Playtest Question:** Can the same migration token be replayed after a successful import or from the wrong profile?

### 9. Local game state is not automatically authoritative game state
**Observation:** Browser-local data can be user-modified and is exposed to same-origin script compromise.

**Mechanism:** Local storage is persistence, not an authentication or authority boundary.

**Generalized Principle:** Portable local saves may restore single-player state, but server-authoritative currency, purchases, ranked results, entitlements and anti-cheat-sensitive facts must be revalidated against their authority source.

**Transfer:** Offline RPG progress can be portable while premium currency remains server-derived.

**Playtest Question:** Which imported fields are accepted as player preference/history, and which must be reconciled with authoritative records?

### 10. PWA installation does not remove origin coupling
**Observation:** Installing a Home Screen web app changes launch UX but does not make its persistence independent of web origin.

**Mechanism:** WebKit documents origin-based quota/storage policy for standalone web apps as well as browser contexts.

**Generalized Principle:** Treat installed-PWA origin changes with the same migration discipline as browser-tab deployments.

**Transfer:** Domain rebranding of iPhone web games, manifest/start_url changes, hosting-provider migration.

**Playtest Question:** Have browser-tab and Home Screen installations both been tested from old origin through migration to new origin?

### 11. Source retirement is a measurable product decision
**Observation:** Removing the old origin too early converts a recoverable migration into permanent local-progress loss for dormant players.

**Mechanism:** Returning players may skip many releases; unlike active users they never executed the migration shell.

**Generalized Principle:** Retire source-origin migration only using evidence: active-save migration rate, returner age distribution, cloud/export coverage, support volume, and compatibility-horizon policy.

**Transfer:** Long-tail browser games, seasonal games, education software, creative tools.

**Playtest Question:** What happens to a player returning after 3, 6, 12, or 24 months without having opened any intermediate build?

### 12. Test an origin matrix, not only a build matrix
**Observation:** CI often tests old-save/new-build combinations on one localhost origin and therefore misses the actual storage isolation failure.

**Mechanism:** Same bytes and code behave differently when the browser origin tuple changes.

**Generalized Principle:** Persistence CI should include origin transitions as first-class fixtures.

**Transfer:** `old-host→new-host`, `http→https`, `subdomain A→B`, browser tab→installed PWA, old origin unavailable, third-party storage blocked.

**Playtest Question:** Does automated QA launch distinct origins and prove that the transfer path—not shared test storage—recovers progress?

## Recommended migration state machine

`DETECT LEGACY POSSIBILITY → ACQUIRE (old-origin export / cloud / manual package) → VERIFY ENVELOPE → STAGE → IDENTITY CHECK → SCHEMA+CONTENT MIGRATION → SEMANTIC VALIDATION → AUTHORITY RECONCILIATION → COMMIT NEW KNOWN-GOOD → ACKNOWLEDGE CLAIM → RETAIN SOURCE FOR HORIZON`

Failure must return to a recoverable state. “No local save on this origin” must never automatically mean “the player has no prior save.”

## QA matrix

At minimum test:
- same origin, new build
- host changed, same schema
- scheme changed (where a historical HTTP deployment existed)
- old save several schema versions behind
- source available / source unavailable
- cloud available / offline only
- valid export / truncated export / future schema / wrong game ID / wrong profile
- destination quota failure before and during commit
- content package missing at destination
- server-authoritative economy disagrees with local portable state
- migration token replay / expiry / wrong account
- browser tab and Home Screen PWA
- private-browsing/nonpersistent context where applicable
- dormant returner skipping every intermediate migration release

## Implementation transfer for smartphone web games

For iPhone/Safari-first games:
1. Keep the canonical public origin stable whenever possible.
2. Before any origin move, ship export support on the old origin.
3. Maintain a minimal old-origin migration shell instead of an immediate redirect-only shutdown.
4. Use explicit portable envelopes and staged import on the new origin.
5. Keep cloud/account reconciliation separate from local-save portability.
6. Preserve source data until destination commit is acknowledged; do not auto-delete old data.
7. Test Home Screen and normal Safari independently.
8. Keep a manual JSON/package export as a last-resort recovery path when appropriate.

## Promotion candidates

Promote to the save guide/playtest framework:
- origin identity is part of persistence compatibility
- redirects do not migrate browser storage
- locate/acquire precedes schema migration
- preserve old-origin migration capability for a compatibility horizon
- portable imports are staged, identity-checked, semantically validated and authority-reconciled
- origin transitions belong in persistence CI
