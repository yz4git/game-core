# Large Batch 34 — Protocol / Version Migration in Networked Games

Date: 2026-09-24

## Scope

Coverage review left protocol/version migration as a high-priority networked-action gap. This batch cross-checks historical platform/version fragmentation context from Gaming Alexandria with modern multiplayer compatibility mechanisms. The goal is not archival reproduction; only reusable abstractions are retained.

Historical cross-sample used as context: Technopolis 1986/1987/1994 and its complete-run history; PC Engine Fan 1988–1997/add-on era; Famimaga 64 1996–1998 and Satellaview/Super Famicom overlap. Modern technical sources: Unity Netcode for Entities protocol checks and `NetworkProtocolVersion`; Photon PUN/Fusion app-version partitioning; PlayFab Multiplayer Server build identity/allocation; Unity Multiplay allocation/version flow; PlayFab Party network-descriptor migration.

## 1. Compatibility is a contract, not a marketing version
**Observation:** A visible game version is too coarse to prove two peers serialize and interpret the same network state.
**Mechanism:** Unity's handshake combines package/game protocol versions with hashes of RPC/command and replicated-component collections.
**Generalized Principle:** Define compatibility from the wire/state contract, not only `1.2.3` labels.
**Transfer:** Compute a compatibility fingerprint from protocol schema, replicated state, rules/content epoch and required feature set.
**Playtest Question:** Can two builds with the same display version but incompatible RPC/state layouts ever enter one session?

## 2. Reject incompatibility before actionable world state
**Observation:** Late discovery of incompatibility turns a clean connection refusal into undefined gameplay.
**Mechanism:** Protocol handshakes can gate connection before normal replication begins.
**Generalized Principle:** Fail closed at the earliest semantic boundary.
**Transfer:** `CONNECT → HELLO → COMPATIBILITY → AUTH → SNAPSHOT → READY`; do not spawn/interact before compatibility passes.
**Playtest Question:** What is the earliest packet at which an incompatible client can alter shared state?

## 3. Exact version equality is safe but unnecessarily fragments populations
**Observation:** Photon can isolate different app versions automatically; useful for safety, costly when builds are actually compatible.
**Mechanism:** Version becomes a matchmaking/session partition key.
**Generalized Principle:** Separate *identity* from *compatibility*.
**Transfer:** Keep build ID for diagnostics, but match on explicit compatibility cohort/range when mixed versions are proven safe.
**Playtest Question:** How much queue population is lost because build IDs differ even though the wire contract does not?

## 4. Compatibility is directional when readers can tolerate older writers
**Observation:** Additive fields/defaults can make A→B safe while B→A is unsafe.
**Mechanism:** Unknown/missing fields and feature use are asymmetric.
**Generalized Principle:** Do not assume compatibility is a symmetric boolean.
**Transfer:** Model `canRead`, `canWrite`, `canJoin`, `canHost` separately where rolling deployment matters.
**Playtest Question:** Does every pair in the supported-version matrix work in both directions, or only one?

## 5. Optional features need capability negotiation, not version guesses
**Observation:** A version number says what build shipped, not which optional protocol features are active.
**Mechanism:** Capability bitsets/feature IDs allow intersection before feature use.
**Generalized Principle:** Negotiate behavior explicitly when graceful degradation is intended.
**Transfer:** Handshake returns required features, optional features and negotiated subset; never infer a feature from semver alone.
**Playtest Question:** Can an older compatible client enter a session where the host later invokes an unsupported optional message?

## 6. Matchmaking must treat protocol compatibility as an invariant
**Observation:** Queue relaxation that crosses an incompatible protocol boundary cannot produce a merely lower-quality match; it produces an invalid one.
**Mechanism:** Compatibility partitions candidate space before skill/QoS ranking.
**Generalized Principle:** Never relax semantic invariants to reduce wait time.
**Transfer:** `compatible cohort → network floor → skill/preferences`; protocol cohort is not a weighted preference.
**Playtest Question:** Can long queue time ever cause two incompatible cohorts to merge?

## 7. Rolling deployment needs an overlap window
**Observation:** Replacing all servers/clients atomically is unrealistic at scale and especially on mobile/web caches.
**Mechanism:** Old and new builds coexist during rollout.
**Generalized Principle:** A deployable protocol change needs a planned compatibility horizon or hard cutover policy.
**Transfer:** Maintain N/N-1 overlap where safe; otherwise drain old sessions and block new cross-version joins.
**Playtest Question:** During rollout, can every client version still in circulation find a valid server without entering an incompatible session?

## 8. Existing sessions and new sessions have different migration policies
**Observation:** A server build can remain valid for a running match even after matchmaking moves new players to a newer build.
**Mechanism:** Session lifetime outlasts allocation policy changes.
**Generalized Principle:** Version rollout policy must distinguish session admission from session continuation.
**Transfer:** Pin protocol/build epoch for the life of a match; route new tickets separately; do not silently hot-swap simulation semantics mid-match.
**Playtest Question:** What happens to a 40-minute match when deployment advances halfway through it?

## 9. Reconnect must return to the session's protocol epoch
**Observation:** Reconnect after app update can present a newer client to an older still-running match.
**Mechanism:** Stable player/session identity survives while executable/protocol identity changes.
**Generalized Principle:** Reconnect compatibility is checked against the session epoch, not only today's latest build.
**Transfer:** Persist `sessionProtocolEpoch` and compatibility fingerprint in reconnect tokens/metadata.
**Playtest Question:** Can update→relaunch→reconnect accidentally attach a new protocol client to an old authoritative state?

## 10. Host migration cannot change protocol truth accidentally
**Observation:** Peer-hosted sessions may elect a replacement host with a different build/capability set.
**Mechanism:** Host election and protocol compatibility are independent dimensions.
**Generalized Principle:** Authority candidates must pass session-epoch compatibility before quality scoring.
**Transfer:** Gate host candidates by protocol/content fingerprint, then rank network/compute quality.
**Playtest Question:** Can the best-latency peer become host even though it cannot faithfully restore the session schema?

## 11. Invitations and reconnect locators are versioned references
**Observation:** PlayFab Party notes that server migration invalidates old network descriptors; version/build migration creates a similar stale-reference problem.
**Mechanism:** External join references can outlive the endpoint/session metadata they identify.
**Generalized Principle:** Join artifacts need expiry and compatibility metadata.
**Transfer:** Invitations carry session ID + protocol epoch + expiry; resolution revalidates current descriptor rather than trusting cached endpoint data.
**Playtest Question:** What does a day-old invite do after two deployments and a server migration?

## 12. Protocol migration requires a fixture corpus, not only current-client tests
**Observation:** Compatibility failures often appear only in old/new pairings that normal same-build CI never exercises.
**Mechanism:** Version-pair state space grows across releases.
**Generalized Principle:** Supported compatibility is a tested matrix.
**Transfer:** Preserve handshake packets, snapshots, commands, reconnect metadata and representative session states for every supported protocol epoch; run pairwise connect/reconnect/join/migrate tests.
**Playtest Question:** Can CI prove every advertised N/N-1 path and reject every unsupported path cleanly?

## Implementation-ready contract

Recommended handshake/session metadata:
- `buildId`
- `protocolEpoch`
- `wireSchemaHash`
- `replicatedStateHash`
- `rulesetEpoch`
- `contentCompatibilityId`
- `requiredCapabilities[]`
- `optionalCapabilities[]`
- `sessionProtocolEpoch`
- `authorityEpoch`

Recommended admission flow:
`TRANSPORT → HELLO → VERSION/FINGERPRINT CHECK → CAPABILITY NEGOTIATION → AUTH → SESSION-EPOCH CHECK → SNAPSHOT → SEMANTIC VALIDATION → READY`

## QA matrix

At minimum test: N↔N, N↔N-1 supported, N↔N-2 rejected, same display version/schema mismatch, additive optional feature, removed required feature, reconnect after client update, old invite after deploy, host migration across mixed builds, rolling server rollout, cached web client after deployment, and unsupported client error/recovery UX.
