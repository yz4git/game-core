## Observations → Mechanisms → Generalized Principles → Transfer → Playtest Questions

### 1. Network architecture is a game-feel decision
**Observation:** Delay-based synchronization waits for remote certainty; rollback proceeds using predicted remote input and corrects divergence later.
**Mechanism:** The architecture chooses where unavoidable latency appears: local input delay, remote correction, or visual discontinuity.
**Generalized Principle:** Do not select netcode only as infrastructure; select the failure artifact that least damages the genre's core skill.
**Transfer:** Frame-sensitive fighting should protect local response; slower strategy may tolerate additional buffering.
**Playtest Question:** Under 100–150 ms RTT, which artifact harms intended decisions most: delayed input, correction, or delayed remote presentation?

### 2. Rollback requires simulation to become a recoverable state machine
**Observation:** GGPO-style rollback restores a prior deterministic state and re-simulates with corrected input.
**Mechanism:** Fast save/load of gameplay state plus deterministic replay turns late input into recoverable history.
**Generalized Principle:** Rollback readiness should be designed into simulation boundaries, not bolted onto presentation code.
**Transfer:** Keep gameplay state serializable and separate particles/audio/UI from authoritative simulation.
**Playtest Question:** Can any gameplay tick be restored and replayed without duplicating one-shot side effects?

### 3. Prediction quality is about change frequency, not intelligence
**Observation:** In fighting games, remote input often remains unchanged for many frames, making "repeat last input" useful.
**Mechanism:** Stable input stretches allow latency to be hidden without sophisticated behavioral prediction.
**Generalized Principle:** Predict the variable with the strongest short-term persistence; complexity is not automatically accuracy.
**Transfer:** Steering/throttle, held guard, continuous movement and charge states can often use simple persistence prediction.
**Playtest Question:** What percentage of predicted frames are correct with the simplest baseline?

### 4. A small fixed delay can reduce visible rollback
**Observation:** Practical rollback systems can combine a small fixed local delay with rollback.
**Mechanism:** A short buffer allows more remote inputs to arrive before prediction while preserving consistent feel.
**Generalized Principle:** Optimize the delay/correction trade-off rather than treating zero-delay as an absolute target.
**Transfer:** Expose an internal test matrix of 0/1/2/3-frame delay versus rollback frequency and magnitude.
**Playtest Question:** Which fixed delay minimizes perceived disruption across typical network conditions?

### 5. Jitter deserves separate treatment from average ping
**Observation:** Snapshot systems buffer updates because arrival spacing varies even when average latency is acceptable.
**Mechanism:** A jitter buffer trades a bounded amount of presentation delay for smoother temporal spacing.
**Generalized Principle:** Network quality is a distribution, not one ping number.
**Transfer:** QA should log RTT median/p95, jitter, packet loss, burst loss, reorder and rollback depth separately.
**Playtest Question:** Does a 60 ms connection with severe jitter feel worse than stable 100 ms, and does telemetry explain why?

### 6. Interpolation intentionally renders remote state in the past
**Observation:** Source-style entity interpolation delays remote presentation so two received states can be blended.
**Mechanism:** Rendering slightly behind authority masks irregular packet arrival and loss.
**Generalized Principle:** Intentional visual latency can improve readability when it is applied to remote/world state rather than local control.
**Transfer:** Remote vehicles and non-local actors may interpolate while the local player's controls remain immediate.
**Playtest Question:** Can the player distinguish local responsiveness from remote smoothing, or does the whole game feel delayed?

### 7. Extrapolation needs a strict horizon
**Observation:** Source limits extrapolation during packet loss because error grows as unseen behavior continues.
**Mechanism:** Beyond a bounded prediction horizon, confident motion becomes fabricated motion.
**Generalized Principle:** Prefer explicit uncertainty/recovery over unlimited prediction.
**Transfer:** After a short dropout, freeze/soft-hold/fade remote actors or transition to reconnect rather than predict indefinitely.
**Playtest Question:** At what dropout duration does continued prediction become more misleading than a visible connection state?

### 8. Lag compensation is an explicit fairness policy
**Observation:** Server-side rewind can evaluate a shot against where a target appeared to the shooter, not only its current server position.
**Mechanism:** Authority temporarily evaluates historical state using measured latency/interpolation.
**Generalized Principle:** Lag compensation decides whose temporal perspective receives priority; its bounds are game rules.
**Transfer:** Define maximum rewind and excluded interactions by genre rather than applying universal compensation.
**Playtest Question:** At high RTT, do both attacker and defender understand apparently contradictory hit outcomes?

### 9. Simulation correction and presentation correction should be separated
**Observation:** State synchronization guidance recommends correcting simulation to valid state while smoothing presentation independently.
**Mechanism:** Blending authoritative physics itself creates invalid intermediate state and can compound errors.
**Generalized Principle:** Correct truth immediately where required; hide the correction only in the visual layer.
**Transfer:** Keep render transforms/camera effects separate from authoritative collision and gameplay transforms.
**Playtest Question:** Does smoothing ever alter collision, hit timing or subsequent physics?

### 10. Mobile QA must test transitions, not only static bad networks
**Observation:** Real mobile play changes between healthy, jittery, lossy, suspended and reconnected states.
**Mechanism:** State transitions expose race conditions and stale authority that steady artificial latency misses.
**Generalized Principle:** Network fault testing should be scenario-based and time-varying.
**Transfer:** Automate Wi-Fi→loss spike→background→resume→reconnect and similar traces.
**Playtest Question:** Does the game recover correctly when the network degrades during a decisive interaction rather than while idle?

### 11. Reconnect is state synchronization, not transport reconnection
**Observation:** Reopening a socket does not establish that client simulation matches current authority.
**Mechanism:** The client needs identity/session validation, authoritative snapshot, sequence baseline and pending-input policy.
**Generalized Principle:** Model reconnect as a resynchronization protocol with explicit states.
**Transfer:** DISCONNECTED → RECONNECTING → AUTHENTICATING → SNAPSHOT → CATCHUP → READY.
**Playtest Question:** Can reconnect ever briefly show an obsolete player/world state as actionable?

### 12. Desync detection must identify the first divergence
**Observation:** Deterministic networking fails when identical inputs produce different states.
**Mechanism:** Periodic checksums reveal mismatch; per-system/state hashes and replay logs localize it.
**Generalized Principle:** "Desynced" is not a useful bug report unless the earliest divergent tick and subsystem can be recovered.
**Transfer:** Store tick, input window, RNG state/version and hierarchical checksums in failure artifacts.
**Playtest Question:** From an automated failure, can a developer reproduce and locate the first divergent tick without the original devices?

### 13. Bandwidth and temporal quality trade against each other
**Observation:** Lower snapshot rates reduce bandwidth but require larger interpolation buffers; higher rates improve temporal fidelity at a bandwidth cost.
**Mechanism:** Sampling frequency determines how much unseen motion the client must reconstruct.
**Generalized Principle:** Optimize network rate against gameplay information frequency, not arbitrary "high tickrate" prestige.
**Transfer:** High-priority combat state can update differently from decorative state.
**Playtest Question:** Which state actually needs high temporal resolution to preserve player decisions?

### 14. Spectator truth can differ from player truth
**Observation:** Source documentation notes spectators do not necessarily see the lag-compensated historical view used for a player's action.
**Mechanism:** Player-facing compensation and observer presentation operate on different timelines.
**Generalized Principle:** Replays/spectators need metadata or reconstruction rules that explain adjudicated outcomes.
**Transfer:** Store authoritative event time plus relevant compensated-time data for contentious hits.
**Playtest Question:** Can a replay make a valid networked hit look impossible?

## Promotions

Cross-source principles strong enough for promotion:
- Netcode architecture is a game-feel/fairness choice, not merely transport infrastructure.
- Jitter/loss/burst behavior must be tested separately from average ping.
- Authoritative simulation correction and visual smoothing should be separate.
- Reconnect must include state resynchronization.
- Automated desync reports should locate first divergence, not only final mismatch.
- Mobile network QA should use changing fault traces.

## Implementation / QA telemetry

Per match/session capture:
- RTT median / p95
- jitter p95
- packet loss and burst-loss length
- out-of-order rate where available
- rollback frames per second
- max rollback depth
- prediction hit rate
- resimulation CPU p95
- correction distance / magnitude
- reconnect attempts / time-to-ready
- desync first tick + subsystem hash

Do not log raw private payloads when aggregate timing/state hashes are sufficient.
