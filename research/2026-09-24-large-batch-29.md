## Modern implementation material sampled

- Steamworks DLC documentation — DLC ownership/installation are explicit runtime states; ownership can be toggled for testing.
- Steamworks ISteamApps — installed/owned/available are distinguishable concepts.
- Minecraft Forge registry documentation — removed/renamed registry objects produce missing mappings with IGNORE/WARN/FAIL/REMAP policies.
- Unity Addressables content-update workflow — published content builds depend on preserved content-state metadata and versioned catalogs.
- Unity Addressables remote distribution — runtime content can change independently from the executable.
- Bethesda Skyrim support material — multiple recovery generations and earlier saves are practical recovery mechanisms when a state no longer loads correctly.

## Observation → Mechanism → Generalized Principle → Transfer → Playtest Question

### 1. A save depends on a content manifest, not only a schema
**Observation:** A structurally valid save can reference DLC, mod, remote asset, quest, item, map or script definitions that are absent in the current runtime.
**Mechanism:** Serialization validity and reference resolvability are separate dimensions.
**Generalized Principle:** Persist a content dependency manifest alongside save schema metadata.
**Transfer:** Record stable content IDs plus package/version/provenance where necessary.
**Playtest Question:** Can the loader explain which required content is absent before mutating the save?

### 2. Missing content is not one failure class
**Observation:** A missing cosmetic, inventory item, active quest script and current-world chunk have very different consequences.
**Mechanism:** References differ in gameplay criticality and reconstruction cost.
**Generalized Principle:** Classify dependencies as OPTIONAL / DEGRADABLE / REQUIRED / WORLD-CRITICAL rather than applying one fallback.
**Transfer:** Cosmetics may use placeholders; required progression logic should block destructive loading.
**Playtest Question:** Does each missing dependency have an explicit policy instead of silently becoming null?

### 3. Identity must be stable across content renames
**Observation:** Forge exposes explicit missing-mapping/remap handling when registry entries disappear or move.
**Mechanism:** Display names and package paths are mutable; persistent identity must survive refactors.
**Generalized Principle:** Save references should use immutable logical IDs and explicit alias/remap tables.
**Transfer:** `old_sword_id → new_sword_id` belongs in migration data, not heuristic string matching.
**Playtest Question:** Can a renamed asset migrate without being mistaken for deleted content?

### 4. Ownership, installation and availability are distinct
**Observation:** Platform APIs distinguish DLC ownership from whether its files are installed/available.
**Mechanism:** Entitlement and local content presence can diverge temporarily or permanently.
**Generalized Principle:** Do not infer entitlement loss from missing local files, or vice versa.
**Transfer:** Model `owned`, `installed`, `available`, `compatible` separately.
**Playtest Question:** What happens when a player owns DLC but launches offline before its files are restored?

### 5. Never normalize a degraded load over the only good save
**Observation:** Loading without dependencies can cause missing objects to disappear from runtime state.
**Mechanism:** A subsequent autosave can convert a temporary dependency problem into permanent data loss.
**Generalized Principle:** Degraded or incomplete loads are read-only until explicitly reconciled.
**Transfer:** Disable autosave/overwrite while unresolved REQUIRED dependencies exist.
**Playtest Question:** Can “open once without DLC, reinstall DLC” restore the exact prior state?

### 6. Preserve unknown data for future restoration
**Observation:** Removed content may later be reinstalled; dropping unknown fields/objects makes restoration impossible.
**Mechanism:** Forward-compatible opaque payload preservation separates “cannot interpret now” from “must delete”.
**Generalized Principle:** Quarantine unresolved content records when safe rather than destructively discarding them.
**Transfer:** Keep opaque component blobs keyed by content ID/version outside active simulation.
**Playtest Question:** After reinstalling the missing package, can quarantined state be rehydrated?

### 7. Fallback must preserve invariants, not merely prevent crashes
**Observation:** Replacing a missing item with null can leave equipment slots, quest counts, economy totals or topology inconsistent.
**Mechanism:** Content participates in higher-level invariants.
**Generalized Principle:** Every fallback requires semantic validation of affected systems.
**Transfer:** Placeholder/remap is followed by inventory, quest, world and progression validation.
**Playtest Question:** Does fallback create impossible progression even though the game boots?

### 8. Current-location dependencies deserve stricter policy
**Observation:** Missing content defining the player's current map/scene/world cell cannot be treated like an absent cosmetic.
**Mechanism:** There may be no valid simulation space into which the avatar can load.
**Generalized Principle:** WORLD-CRITICAL dependency loss requires restore/reinstall or a deliberately designed evacuation path.
**Transfer:** Optional safe-hub relocation must be explicit, validated and reversible.
**Playtest Question:** Can relocation strand quests, companions or return portals?

### 9. Content update metadata is part of compatibility history
**Observation:** Unity Addressables content-update workflows require preservation of build content-state metadata to construct compatible updates.
**Mechanism:** Runtime executable version alone cannot reconstruct which content catalog a save originally referenced.
**Generalized Principle:** Archive released content manifests/catalog identities with save fixtures.
**Transfer:** CI should load historical saves against the exact historical manifest and supported upgrade paths.
**Playtest Question:** Can QA reproduce a save created three content catalogs ago?

### 10. Missing-content UX should be actionable
**Observation:** “Save corrupted” conflates malformed bytes with absent dependencies.
**Mechanism:** Players choose different recovery actions depending on whether they need reinstall, enable, update, remap or restore.
**Generalized Principle:** Diagnose dependency mismatch separately from corruption.
**Transfer:** Show affected package/category and safe actions without exposing internal implementation noise.
**Playtest Question:** Can a player tell whether to reinstall content or choose an older save?

### 11. Test removal and restoration as a round trip
**Observation:** One-way “game still launches after mod removal” tests miss permanent state loss.
**Mechanism:** Compatibility quality is revealed when the dependency returns.
**Generalized Principle:** Missing-content QA should include remove → degraded inspection → restore → equality/semantic comparison.
**Transfer:** Hash stable subsystems and compare important semantic summaries after restoration.
**Playtest Question:** What state fails to return after the dependency is re-enabled?

### 12. Dependency closure matters
**Observation:** One DLC/mod can depend on another package or content catalog.
**Mechanism:** Checking only directly referenced packages misses transitive absence.
**Generalized Principle:** Validate dependency closure before loading authoritative state.
**Transfer:** Produce a resolved manifest with required/transitive dependency status.
**Playtest Question:** Can a package appear installed while one of its required dependencies is unavailable?

### 13. Shared/multiplayer saves need participant capability checks
**Observation:** Content available to a host may be unavailable to another participant.
**Mechanism:** State can contain definitions some clients cannot render or simulate.
**Generalized Principle:** Shared-state compatibility requires negotiated content capability, not host-only validation.
**Transfer:** Separate authoritative required content from presentation-only optional content.
**Playtest Question:** Does joining with a missing package fail early and explain why rather than desync later?

### 14. Content removal is a fault-injection dimension
**Observation:** Platforms such as Steam explicitly support testing DLC ownership changes; registry systems expose missing-entry policies.
**Mechanism:** Dependency loss can be simulated systematically.
**Generalized Principle:** Add content presence/ownership/version permutations to save CI.
**Transfer:** Fixture matrix: owned+installed, owned+missing, not-owned, old-version, renamed/remapped, dependency missing, restored.
**Playtest Question:** Which permutation can erase or silently rewrite recoverable progress?

### 15. Content tombstones prevent accidental ID reuse
**Observation:** Deleted content IDs may remain embedded in years of saves.
**Mechanism:** Reusing an old persistent ID for unrelated new content can falsely resolve historical references.
**Generalized Principle:** Retire persistent IDs permanently or version their namespace.
**Transfer:** Maintain tombstone registry for shipped IDs.
**Playtest Question:** Can any removed ID resolve to semantically unrelated content in a newer build?

### 16. Compatibility support needs an explicit horizon
**Observation:** Long-lived games accumulate old schemas, catalogs, mods and DLC combinations that cannot all be supported forever.
**Mechanism:** Undefined support boundaries turn failures into surprises.
**Generalized Principle:** Define and test a compatibility horizon: migrate, read-only recover, export, or explicitly unsupported.
**Transfer:** Preserve fixtures at boundary versions and document safe upgrade stepping stones.
**Playtest Question:** What is the oldest supported content/save combination, and does failure beyond it preserve user data?

## Implementation model

Suggested save metadata:

```text
saveSchemaVersion
saveUUID
revision
baseGameContentVersion
contentManifestHash
dependencies[] {
  stableContentId
  packageId
  packageVersion
  criticality
  provenance
}
unresolvedOpaqueState[]
```

Load states:

`PREFLIGHT → DEPENDENCY_CHECK → {READY | DEGRADED_READONLY | BLOCKED_RECOVERABLE | UNSUPPORTED} → MIGRATE → VALIDATE → PLAYABLE`

Never enter normal autosave from `DEGRADED_READONLY`.

## CI matrix

- DLC disabled then restored
- DLC owned but files unavailable
- optional cosmetic removed
- equipped item definition removed
- active quest/script removed
- current map/world package removed
- registry ID renamed with remap
- registry ID removed without remap
- transitive dependency missing
- old remote catalog unavailable
- newer content with older executable
- opaque unknown component round-trip
- degraded load followed by accidental autosave attempt
- content restored and semantic equality checked
- tombstoned ID reuse test

## Promotion candidates

Strong enough for cross-system promotion:
- schema compatibility and content compatibility are separate dimensions
- degraded loads must not overwrite known-good state
- persistent IDs need explicit remapping/tombstones
- recovery UX must distinguish missing dependencies from corruption
- compatibility testing should include removal-and-restoration round trips
