# Large Batch 31 — Host / Authority Migration Under Dropout

Date: 2026-09-24

## Scope

High-priority gap selected from `research/COVERAGE.md`: host/authority migration under dropout. Historical context was cross-checked against Gaming Alexandria's preserved late-1980s/1990s arcade and console material (Play Meter 1990 directory, Famimaga 64 1996–1998 holdings, and broader magazine index), then compared with public implementation material from Unity Multiplayer Sessions, legacy UNet host migration, Photon Fusion reconnect/host migration, Photon PUN ownership/control, PlayFab Lobby ownership migration, and Microsoft's DirectPlay peer-to-peer host-migration protocol documentation.

## New observations

### 1. Host election and world-state migration are separate problems
**Observation:** Modern session APIs can elect a new session owner without transferring synchronized gameplay state.

**Mechanism:** Membership/metadata authority and simulation authority have different state and consistency requirements.

**Generalized Principle:** Never treat `newHostId` as proof that the match is recoverable. Migration succeeds only after authority, authoritative state, identity mapping, and progression clocks are all reconstructed.

**Transfer:** Model `HOST_ELECTED` and `WORLD_RESTORED` as separate states.

**Playtest Question:** Can the UI say “reconnected” while gameplay state is still incomplete or stale?

### 2. A migration snapshot is a recovery checkpoint, not merely replication data
**Observation:** Photon Fusion requires a pushed host-migration snapshot before a client-host session can be rebuilt.

**Mechanism:** Once the sole authority disappears, ordinary replication cannot request missing truth from it.

**Generalized Principle:** Peer-hosted games need an independently survivable recovery representation before failure occurs.

**Transfer:** Maintain periodic compact migration checkpoints with tick, object identity, ownership, RNG/sequence state, match phase and integrity/version metadata.

**Playtest Question:** If the host process vanishes without a final packet, what exact state can survivors reconstruct?

### 3. Recovery-point age is a gameplay fairness variable
**Observation:** Periodic migration snapshots imply some interval between current play and the latest recoverable authority state.

**Mechanism:** Longer checkpoint intervals reduce bandwidth/CPU but increase rollback of acknowledged gameplay after host loss.

**Generalized Principle:** Set migration checkpoint cadence from acceptable lost-gameplay time, not convenience alone.

**Transfer:** Telemetry should record `migration_snapshot_age_ms` at failure and restored tick distance.

**Playtest Question:** How many seconds of confirmed-looking actions can disappear after a worst-timed host loss?

### 4. Stable player identity must survive transport reconnection
**Observation:** Legacy Unity host migration preserved old connection identity so reconnecting clients could be matched to prior player objects; Photon reconnect designs likewise need stable session identity/tokens.

**Mechanism:** A new socket/connection ID is not the same thing as the player's persistent match identity.

**Generalized Principle:** Separate transport identity from match identity.

**Transfer:** Use stable match-scoped player IDs and reconnect credentials; never key inventory, score, ownership or avatar continuity only by current socket ID.

**Playtest Question:** Can reconnect create a duplicate avatar, duplicate reward owner, or orphan the original entity?

### 5. Ownership needs an explicit orphan policy
**Observation:** Photon distinguishes object ownership/control behavior when a peer disconnects; some objects persist while control transfers, others are cleaned up.

**Mechanism:** Player departure can leave entities whose existence and authority lifetimes differ from the player's connection lifetime.

**Generalized Principle:** Every authoritative entity class should declare what happens when its owner disappears: transfer, freeze, AI-takeover, persist-unowned, expire, or destroy.

**Transfer:** Add `disconnectPolicy` to network entity definitions and test soft vs hard disconnect separately.

**Playtest Question:** Which objects become duplicated, inert, invulnerable or prematurely destroyed when their owner drops?

### 6. Election must be deterministic or externally arbitrated
**Observation:** DirectPlay's peer migration selected a surviving peer from shared membership ordering, while PlayFab exposes explicit automatic/manual/server ownership policies.

**Mechanism:** If survivors independently choose different authorities, split-brain becomes possible.

**Generalized Principle:** Election needs one shared deterministic rule or an external service decision, plus an epoch/term that makes older authority invalid.

**Transfer:** Persist `authorityEpoch`; accept authoritative writes only from the current epoch.

**Playtest Question:** Under asymmetric packet loss, can two survivors both believe they are host?

### 7. Host quality should influence election, but only among eligible consistent peers
**Observation:** “Any surviving peer” maximizes continuity but may choose a weak network/device; arbitrary owner selection is available in some lobby systems but is not necessarily simulation-optimal.

**Mechanism:** Host suitability combines state freshness, protocol/content compatibility, connectivity and compute headroom.

**Generalized Principle:** Election score comes after correctness gates.

**Transfer:** Eligibility first: compatible build/protocol, sufficient checkpoint/state, authenticated member, no integrity failure. Then rank by measured network stability and sustained simulation headroom.

**Playtest Question:** Does the fastest-ping candidate lack the newest recoverable state or enough CPU to host rollback bursts?

### 8. Lobby ownership and simulation authority must not be conflated
**Observation:** PlayFab can migrate lobby ownership independently, while server-owned lobbies use different recovery semantics; Unity similarly separates session host election from network-state migration.

**Mechanism:** Social/session metadata has weaker consistency requirements than gameplay truth.

**Generalized Principle:** Represent lobby owner, matchmaking/session owner, simulation authority and per-object authority as distinct roles even if one peer normally holds all of them.

**Transfer:** Log role transitions independently.

**Playtest Question:** Can changing lobby owner accidentally grant gameplay authority or vice versa?

### 9. Migration requires a freeze/barrier for actionable inputs
**Observation:** During authority loss there is an interval where no survivor can safely know which unacknowledged actions became canonical.

**Mechanism:** Continuing to accept gameplay during election/restoration creates divergent branches that later need destructive reconciliation.

**Generalized Principle:** Prefer a short explicit migration barrier over invisible speculative divergence beyond the recovery envelope.

**Transfer:** `HOST_LOST → FREEZE_INPUT_COMMIT → ELECT → RESTORE → VERIFY → RESUME`; presentation may continue but authoritative actions are queued or rejected according to policy.

**Playtest Question:** What happens to an attack, purchase, pickup or finish-line crossing issued during the migration window?

### 10. Migration completion needs semantic invariants, not just successful deserialization
**Observation:** A snapshot can load while ownership, timers, uniqueness constraints or match phase are inconsistent.

**Mechanism:** Serialization validity proves bytes are readable, not that the world is legally resumable.

**Generalized Principle:** Validate gameplay invariants before reopening input.

**Transfer:** Check unique player/entity IDs, authority ownership, monotonic score/progression, timer phase, RNG/event sequence, objective ownership and pending transaction IDs.

**Playtest Question:** Can a technically restored match contain two flag owners, duplicate unique pickups, or a timer that moved backward?

### 11. Host return is not automatic authority restoration
**Observation:** After migration, the old host may reconnect as an ordinary peer while a newer authority epoch exists.

**Mechanism:** Restoring authority based on historical role can resurrect stale state.

**Generalized Principle:** Authority is epoch-scoped, not identity-scoped.

**Transfer:** A returning former host must join through normal resync and cannot publish old authoritative state unless an explicit handoff protocol advances the epoch.

**Playtest Question:** Can the old host reconnect and overwrite progress made after migration?

### 12. Migration UX is part of perceived fairness
**Observation:** Legacy Unity explicitly notes that production games need custom host-migration UI rather than prototype controls.

**Mechanism:** A technically correct pause looks like lag or a crash unless players understand that actions are temporarily non-authoritative.

**Generalized Principle:** Expose migration state, preserve player intent where safe, and distinguish “reconnecting” from “restoring match.”

**Transfer:** Show concise stages such as `HOST LOST / RESTORING MATCH / SYNCING / RESUMING`; do not show success before semantic validation.

**Playtest Question:** Can players tell whether their last action counted and when control is safe again?

## Implementation-ready state machine

```text
RUNNING(epoch N)
  → HOST_SUSPECTED
  → HOST_LOST
  → COMMIT_BARRIER
  → ELECT_CANDIDATE
  → HOST_ELECTED(epoch N+1)
  → LOAD_MIGRATION_CHECKPOINT
  → REBIND_PLAYER_AND_OBJECT_AUTHORITY
  → APPLY_ACCEPTED_POST_CHECKPOINT_EVENTS (only if provable)
  → SEMANTIC_VALIDATE
  → RESYNC_PEERS
  → READY_BARRIER
  → RUNNING(epoch N+1)
```

Failure exits should be explicit: `RETRY_ELECTION`, `FALLBACK_SERVER`, `RETURN_TO_LOBBY_WITH_RESULT`, or `MATCH_ABORTED_RECOVERABLE`. Never silently continue from an unverified partial world.

## Minimum migration checkpoint

- protocol/build/content version
- match/session ID
- authority epoch + checkpoint tick
- stable player IDs and membership
- authoritative world state or reconstructable state
- per-object authority/ownership
- match phase and timers
- RNG/event sequence identifiers
- committed score/economy/objective state
- dedupe IDs for one-shot grants/events
- integrity hash/checksum

## Telemetry

Record at minimum:
- host-loss cause classification
- election duration
- restore duration
- total input-unavailable duration
- checkpoint age at loss
- restored tick distance
- candidate rejection reasons
- number of reconnect attempts
- orphaned/transferred entity count
- semantic validation failures by invariant
- post-migration desync rate
- match completion rate after migration
- player quit rate within 60 s of migration

## Fault-injection matrix

Inject host loss during:
- quiet traversal
- simultaneous combat/hit resolution
- unique pickup/reward grant
- score/goal/finish adjudication
- scene/round transition
- object ownership transfer
- client reconnect
- high jitter/burst loss
- background/suspend on mobile host
- checkpoint creation itself

Repeat with 2, 3, 4+ peers and with asymmetric connectivity so survivors do not all detect loss simultaneously.

## Promotion candidates

Cross-source findings strong enough for reuse:
1. election != state migration;
2. transport identity != match identity;
3. lobby ownership != simulation authority;
4. authority must be epoch-scoped;
5. resume only after semantic validation;
6. checkpoint age is a fairness budget;
7. every network entity needs an owner-disconnect policy;
8. migration QA must inject failures at transaction boundaries, not only during idle play.
