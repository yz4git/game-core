# Large Batch 30 — Semantic Save Merge / Divergent Progression

Date: 2026-09-24

## Scope

Coverage review showed that save corruption, schema migration, browser quota, and missing DLC/mod content were already well covered, while **semantic merge of independent progression branches** remained high priority. This batch therefore studies what happens when two valid saves descend from the same ancestor and both contain meaningful progress.

Historical context was cross-sampled from Gaming Alexandria holdings across several eras and publication types: LOGiN (1983–1987), Program Pochette (1984–1987 and preserved runnable reader programs), Family Computer Magazine (1985–1990), Play Meter (1978/1988/1990), Game Hihyō (1994–2006), and Famimaga 64 (1996–1998). These sources provide contrasting contexts for local persistence, passwords/continues, arcade session value, user-created software, criticism/strategy culture, and later console progression. No magazine text or images are reproduced here.

Modern implementation references included PlayFab Game Saves conflict/atomic-unit documentation, PlayFab Game Saves product material, Unity Cloud Save write locks/API, and distributed-data merge concepts. The reusable result is not a vendor-specific sync recipe: it is a semantic model for deciding which game state can be joined automatically and which state requires an explicit branch choice.

## New observations / mechanisms

### 1. A cloud conflict is a history problem, not a timestamp contest
**Observation:** Two devices can both contain legitimate progress after their last common sync.

**Mechanism:** `latest timestamp wins` collapses a branch graph into a total order and can erase achievements made on the other branch.

**Generalized Principle:** Persist enough ancestry to distinguish stale copies from true divergent branches.

**Transfer:** Store `saveId`, `revisionId`, `parentRevisionId` (or compact ancestry token), device/session provenance, and a semantic summary.

**Playtest Question:** After two devices progress offline in different ways, can the system explain that both changed rather than calling one merely “older”?

### 2. Merge policy belongs to each field/domain, not to the save blob
**Observation:** Some state is naturally unionable while other state represents one mutually exclusive world history.

**Mechanism:** A whole-save merge applies one policy to heterogeneous semantics.

**Generalized Principle:** Classify persisted domains by algebra before implementing automatic merge.

**Transfer:** Examples: discovered codex entries may use set union; monotonic achievements may use union; best score may use max; consumable balance usually must not use max or sum; current quest branch may require conflict resolution.

**Playtest Question:** For every persisted field, can the team state why its merge operator preserves gameplay meaning?

### 3. Commutative merge is valuable only when the game rule is also commutative
**Observation:** Set union and max converge mechanically regardless of arrival order.

**Mechanism:** Technical convergence can still violate game semantics—for example, combining mutually exclusive faction unlocks.

**Generalized Principle:** Never infer semantic safety from CRDT-like convergence alone.

**Transfer:** Put game invariants after the merge operator and reject/reclassify merges that produce impossible combinations.

**Playtest Question:** Can A⊔B converge perfectly yet create a progression state no legal playthrough can reach?

### 4. Currency and consumables need provenance, not arithmetic guessing
**Observation:** Branch A can spend a resource while branch B earns or spends the same resource.

**Mechanism:** `max(balance)` duplicates spending power; `sum(balance)` duplicates the common ancestor balance; `min(balance)` destroys legitimate earnings.

**Generalized Principle:** Non-monotonic economies cannot be safely merged from final balances alone.

**Transfer:** If cross-device merge is required, retain authoritative transaction/event IDs or keep the economy server-authoritative. Otherwise force branch choice for that domain.

**Playtest Question:** Can offline branching produce free currency, duplicate unique items, or erase a legitimate purchase?

### 5. Unique rewards require identity-level deduplication
**Observation:** Both branches may earn the same one-time reward independently.

**Mechanism:** Adding inventory counts duplicates the reward; choosing one entire branch may discard unrelated progress.

**Generalized Principle:** One-time grants need stable grant/reward IDs distinct from display item IDs.

**Transfer:** Merge the set of grant IDs, then derive or validate inventory effects.

**Playtest Question:** If the same boss reward is earned on both devices, is it represented once after reconciliation?

### 6. Quest/world state is often a partial order, not a numeric maximum
**Observation:** Narrative branches can diverge into states that are individually valid but mutually exclusive.

**Mechanism:** Treating quest stage numbers as ordered progress assumes all stages lie on one line.

**Generalized Principle:** Represent irreversible narrative decisions explicitly and detect incompatible branch facts.

**Transfer:** Use stable decision/event IDs and declared exclusivity groups; auto-merge only compatible facts.

**Playtest Question:** Can two opposing choices accidentally coexist after sync because one had a larger stage number?

### 7. Deletion needs tombstone semantics
**Observation:** One branch may delete/dismantle/drop an object while another branch leaves the ancestor copy unchanged.

**Mechanism:** Absence alone cannot distinguish “never existed”, “not loaded”, and “explicitly deleted”.

**Generalized Principle:** For mergeable persistent identities, deletion is data.

**Transfer:** Keep tombstones or operation provenance through the reconciliation horizon, then compact only after all relevant ancestors are obsolete.

**Playtest Question:** Can an item or user-created object resurrect after another device deliberately deleted it?

### 8. Atomic-unit boundaries should follow invariants
**Observation:** PlayFab detects conflicts at atomic units; independent units can sync without conflict, while changes within the same unit are reconciled together.

**Mechanism:** Bad partitioning either creates needless conflicts or permits dependent values to split across versions.

**Generalized Principle:** Choose sync/atomic boundaries around gameplay invariants, not convenient filenames.

**Transfer:** Keep tightly coupled world state together; separate truly independent slots, settings, photo/replay metadata, or unlock collections where safe.

**Playtest Question:** If half of a coupled subsystem comes from each branch, can the result violate an invariant?

### 9. Optimistic concurrency detects races; it does not solve semantic conflicts
**Observation:** Unity Cloud Save write locks can reject a write made against stale state.

**Mechanism:** A version token tells you the base changed, but not whether inventory, quests, or unlocks can be merged.

**Generalized Principle:** Separate conflict **detection** from conflict **resolution**.

**Transfer:** On lock failure, refetch, compute ancestry/semantic diff, apply domain policies, validate, then retry against the new lock.

**Playtest Question:** Does a retry loop merely overwrite the winner, or does it re-evaluate the changed gameplay state?

### 10. Conflict UX should preview semantic loss
**Observation:** Players cannot meaningfully choose between opaque timestamps or filenames.

**Mechanism:** Conflict resolution is a decision under uncertainty; hiding progression deltas makes accidental loss likely.

**Generalized Principle:** Show the consequences of choosing or merging branches in game terms.

**Transfer:** Preview chapter/location, playtime, major unlocks, unique items, quest decisions, currency delta, and unsynced session provenance.

**Playtest Question:** Before confirming, can a player identify the important progress that each option would discard?

### 11. Auto-merge needs a post-merge legality proof
**Observation:** Individually safe domain operators can interact to create an impossible composite state.

**Mechanism:** Inventory, quest, world, equipment, and economy invariants cross subsystem boundaries.

**Generalized Principle:** Treat merged state as an untrusted migration candidate until global semantic validation passes.

**Transfer:** Stage merged candidate → validate local invariants → validate cross-domain invariants → compare semantic summary → commit transactionally.

**Playtest Question:** Can the merge ever commit before all global invariants and references have been checked?

### 12. Preserve both parents until the merge proves durable
**Observation:** A plausible merge may reveal corruption or semantic loss only after load or later validation.

**Mechanism:** Deleting parent branches immediately removes the evidence and recovery path.

**Generalized Principle:** A merge commit should have a recovery horizon just like schema migration.

**Transfer:** Retain both parent revisions and the merge manifest until the candidate has survived validation and a later known-good checkpoint.

**Playtest Question:** Can support/QA reconstruct both original branches after a bad automatic merge?

### 13. Three-way semantic diff is safer than two-way comparison
**Observation:** Comparing only A and B cannot tell which values changed from their common state.

**Mechanism:** A common ancestor separates unchanged inherited data from actual branch edits.

**Generalized Principle:** When ancestry is available, reconcile `base → A` and `base → B`, not merely A versus B.

**Transfer:** Generate per-domain change sets relative to the lowest known common revision; only collide edits that touch incompatible semantics.

**Playtest Question:** Does an unchanged old value on one branch incorrectly override a genuine change on the other?

### 14. Mergeability should be designed before shipping offline progression
**Observation:** Final-state snapshots often omit the provenance later needed for safe reconciliation.

**Mechanism:** Once shipped, reconstructing grant IDs, decision identity, deletion history, or transaction ancestry may be impossible.

**Generalized Principle:** Offline/cloud save architecture is part of progression-system design, not a storage afterthought.

**Transfer:** During feature design, declare identity, monotonicity, exclusivity, authority, merge operator, validation rule, and recovery policy for every persistent domain.

**Playtest Question:** If this feature changes on two devices offline today, what exact information would tomorrow's merge need?

## Implementation pattern

Recommended reconciliation pipeline:

`LOAD METADATA → FIND COMMON ANCESTOR → SEMANTIC DIFF A/BASE + B/BASE → CLASSIFY DOMAINS → AUTO-MERGE SAFE DOMAINS → SURFACE UNSAFE CONFLICTS → BUILD CANDIDATE → GLOBAL VALIDATE → TRANSACTIONAL COMMIT → RETAIN PARENTS`

Suggested merge-policy table fields:

- domain/key
- persistent identity strategy
- authority source
- monotonic? yes/no
- legal merge operator
- exclusivity/invariant group
- deletion/tombstone policy
- provenance required
- automatic / assisted / branch-choice-only
- post-merge validator

## QA matrix

At minimum test:

- same ancestor, only A changed
- same ancestor, only B changed
- independent domains changed on each branch
- same monotonic unlock earned independently
- same unique reward earned independently
- currency earned on A / spent on B
- same item deleted on A / modified on B
- mutually exclusive quest decisions
- world transition on A / inventory mutation on B
- write-lock race during reconciliation
- merge candidate validation failure
- crash before merge commit
- crash after merge commit but before parent cleanup
- repeated reconciliation is idempotent
- A⊔B and B⊔A produce the same result for domains declared commutative
- restore both parents after a deliberately bad merge
