## 1. Calibration drift is game-balance drift
**Observation:** Arcade service manuals expose calibration values and invalid-calibration states for aiming/physical controls.
**Mechanism:** The same player action maps to a different in-game result as hardware/input drift changes.
**Generalized Principle:** Input calibration is part of game balance whenever success depends on spatial precision.
**Transfer:** Touch dead-zone, virtual-stick center, gyro neutral and controller axis ranges should be versioned/tested like gameplay parameters.
**Playtest Question:** Can identical physical intent produce materially different success rates across devices or after a long session?

## 2. Invalid calibration must be diagnosable, not merely felt
**Observation:** Service interfaces can explicitly expose invalid calibration and stored offsets.
**Mechanism:** Operators can distinguish hardware/input faults from player difficulty.
**Generalized Principle:** Precision-input systems need observable calibration health.
**Transfer:** Add debug overlays for touch center, axis range, gyro bias and sampled latency.
**Playtest Question:** When control feels wrong, can QA identify the failing layer without guessing?

## 3. Maintenance burden constrains viable mechanics
**Observation:** Coin-op manuals devote operational tooling to switches, sensors, dispensers, calibration and component tests.
**Mechanism:** A mechanic depending on a fragile sensor becomes unavailable when that sensor degrades.
**Generalized Principle:** The more central an input/device is, the cheaper its health check and fallback must be.
**Transfer:** Mobile games relying on haptics/gyro/audio timing need fallback controls and capability tests.
**Playtest Question:** What remains playable when the special input is unavailable or unreliable?

## 4. Test mode is a product feature for maintainers
**Observation:** Operator manuals provide dedicated I/O and network tests rather than asking staff to infer failures from normal play.
**Mechanism:** Direct observability shortens diagnosis and reduces accidental configuration changes.
**Generalized Principle:** Build explicit diagnostics for systems whose failure can masquerade as game-design problems.
**Transfer:** Internal game builds should expose input, save, network, audio and procedural-health checks.
**Playtest Question:** Can a tester prove that input/network/save is healthy before tuning difficulty?

## 5. Linked multiplayer needs explicit identity topology
**Observation:** Linked racing cabinets require unique cabinet IDs, total cabinet count and a defined server/primary role.
**Mechanism:** Shared simulation depends on unambiguous participant identity and topology.
**Generalized Principle:** Multiplayer setup must make identity, membership and authority explicit before gameplay begins.
**Transfer:** Web multiplayer should expose room membership, host/server role and reconnect identity rather than relying on implicit ordering.
**Playtest Question:** After disconnect/reconnect, can every participant tell who is authoritative and whether they rejoined the same session?

## 6. Network setup order is part of reliability design
**Observation:** Linked-cabinet manuals specify safe configuration/power/link order to avoid network misconfiguration.
**Mechanism:** Initialization races can create persistent wrong identities or failed sessions.
**Generalized Principle:** Multiplayer startup should be an idempotent state machine, not an assumed happy-path sequence.
**Transfer:** Test join-before-host-ready, refresh during join, duplicate identity, stale room and reconnect cases.
**Playtest Question:** Does repeating or interrupting setup converge to a valid state without manual reset?

## 7. Linked play requires a network-specific diagnostic path
**Observation:** Cabinets include network test screens separate from ordinary gameplay.
**Mechanism:** Link faults otherwise appear as gameplay lag, missing rivals or failed starts.
**Generalized Principle:** Separate connectivity health from match-quality evaluation.
**Transfer:** Record RTT/jitter/loss/reconnect and simulation correction separately from win/loss telemetry.
**Playtest Question:** Can QA distinguish poor network health from poor prediction/rollback design?

## 8. Reward tables require monotonic invariants
**Observation:** Redemption manuals warn that payout threshold tables need progressively increasing score requirements to avoid unpredictable payout behavior.
**Mechanism:** Misordered configuration violates the assumed mapping from performance to reward.
**Generalized Principle:** Designer/operator-editable economy tables need machine-checked invariants.
**Transfer:** Validate XP curves, loot tiers, rank thresholds and score rewards on load/build.
**Playtest Question:** Can any configuration produce a better reward for objectively worse performance?

## 9. Reward floors and caps are safety rails, not balance substitutes
**Observation:** Redemption systems expose minimum/maximum payout controls.
**Mechanism:** Bounds limit catastrophic outcomes while leaving the central reward function intact.
**Generalized Principle:** Put hard safety bounds around variable reward systems, then balance behavior inside them.
**Transfer:** Cap farming rate, compensation grants and procedural jackpot outcomes without flattening all rewards.
**Playtest Question:** What is the worst possible reward cost/output over 10,000 simulated sessions?

## 10. Dynamic payout targets can conflict with perceived skill causality
**Observation:** Skill-based redemption can combine player performance with a target payout system.
**Mechanism:** Hidden adjustment can make equally skilled actions produce economically different outcomes.
**Generalized Principle:** If a system adapts rewards behind the scenes, protect the legibility of skill-to-result causality.
**Transfer:** Dynamic progression/economy correction should avoid changing immediate combat/score outcomes in ways players read as cheating.
**Playtest Question:** Can two visibly equivalent successes receive unexplained materially different rewards?

## 11. Audits should drive configuration, not intuition alone
**Observation:** Operator systems expose audits alongside adjustable timers, lives, payout and attract settings.
**Mechanism:** Operators can compare configuration against actual use rather than relying only on impressions.
**Generalized Principle:** Every live-tunable parameter should have a paired outcome metric.
**Transfer:** Session timer ↔ completion/replay; difficulty ↔ failure location; reward rate ↔ behavior mix; control sensitivity ↔ correction/miss rate.
**Playtest Question:** For each tuning knob, which telemetry tells us whether the change helped?

## 12. Factory reset and persistent records have different lifetimes
**Observation:** Some operator reset functions restore settings without clearing audits/high scores.
**Mechanism:** Configuration state and historical evidence serve different purposes.
**Generalized Principle:** Separate reset domains: preferences/configuration, progression, diagnostics/audits and competitive records.
**Transfer:** Save-system recovery should not erase telemetry or leaderboard evidence merely because settings are reset.
**Playtest Question:** Does each reset option state exactly which data classes survive?

## Promoted principles

Cross-source evidence is strong enough to promote:
1. Calibration drift is gameplay/balance drift.
2. Critical subsystems require explicit health diagnostics.
3. Multiplayer initialization must converge safely after interruption/repetition.
4. Editable economy curves require invariant validation and hard safety bounds.
5. Live-tunable parameters need paired outcome telemetry.
6. Reset domains should separate configuration from history/evidence.

## Implementation transfer

For iPhone/Web projects, add a compact diagnostic mode capable of reporting pointer/touch center and ranges, gamepad axes/dead-zones, AudioContext state/latency estimate, network RTT/jitter/loss where applicable, save schema/version, and generator/replay version. Keep this separate from player-facing difficulty controls.

For linked/network play, model setup explicitly as discover → identify → join → synchronize → ready → play → reconnect/leave, and fuzz interruption at every transition.

For any score→currency/reward mapping, validate monotonic thresholds at build/load time and simulate worst-case payout/reward-per-minute before release.
