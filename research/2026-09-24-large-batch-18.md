## Observation → Mechanism → Generalized Principle → Transfer → Playtest Question

### 1. Save format is a long-lived compatibility contract
**Observation:** Long-running games outlive individual data layouts; modern migration systems therefore attach an explicit format version and preserve migrations from older releases.
**Mechanism:** A player may skip many game versions, so the loader must understand a historical state, not only the immediately previous build.
**Generalized Principle:** Treat every shipped save schema as an API version that may return years later.
**Transfer:** Add `schemaVersion` to localStorage/JSON saves in web games and keep deterministic migration steps in source control.
**Playtest Question:** Can a save fixture from every released schema still reach the current schema without manual editing?

### 2. Sequential migrations localize failure
**Observation:** Migration guidance commonly favors explicit v1→v2→v3 steps rather than a single opaque old→current conversion.
**Mechanism:** Small transformations are easier to test, diagnose, roll forward, and preserve than one giant compatibility function.
**Generalized Principle:** Prefer composable, monotonic migrations with one responsibility per step.
**Transfer:** Keep migration registry + fixture test per historical version.
**Playtest Question:** When migration fails, can QA identify the exact transition and field responsible?

### 3. A successful parse is not proof of a valid save
**Observation:** Corruption may leave a file syntactically readable while references, ranges, identities, or world invariants are broken.
**Mechanism:** Serialization validity and game-state validity are different layers.
**Generalized Principle:** Validate semantic invariants after deserialization and after every migration.
**Transfer:** Check required IDs, finite numbers, enum ranges, inventory bounds, map/progression consistency, and impossible states before committing the loaded state.
**Playtest Question:** Can malformed-but-parseable fixtures enter gameplay?

### 4. Never destroy the last known-good state while writing the next one
**Observation:** Recovery tools and platform guidance rely on backups/version history because interrupted or defective writes can make the newest state unusable.
**Mechanism:** Saving is a transaction; replacing the only good copy before validating the new one converts a transient failure into permanent loss.
**Generalized Principle:** Write candidate → validate → commit; retain at least one known-good generation.
**Transfer:** For web saves, write a staging key/object, checksum/validate it, then advance the active pointer; rotate previous generations.
**Playtest Question:** What survives if the process is killed at every possible point in the save transaction?

### 5. Recovery should be read-only until a valid source is chosen
**Observation:** Save-recovery tooling emphasizes inspecting backups without modifying originals first.
**Mechanism:** Repair attempts themselves can erase forensic evidence or the only recoverable copy.
**Generalized Principle:** Diagnose first, copy second, mutate last.
**Transfer:** A recovery UI should show active/backup generations and restore by copying into a new candidate before replacing active state.
**Playtest Question:** Can a failed recovery attempt make the original situation worse?

### 6. Cloud sync is a conflict-resolution system, not merely upload/download
**Observation:** PlayFab Game Saves explicitly includes conflict handling, active-device scenarios, offline play, timestamps/versioning, and cross-device synchronization.
**Mechanism:** Two valid saves can diverge independently; “newest timestamp wins” may discard unique progress.
**Generalized Principle:** Treat sync conflicts as competing histories whose meaning depends on game semantics.
**Transfer:** Store revision, device/session ID, logical progress summary, and parent/base revision; show a human-readable choice when automatic merge is unsafe.
**Playtest Question:** Can two devices make valid offline progress and reconnect without silently losing the branch the player wanted?

### 7. Conflict UI should describe consequences, not filenames
**Observation:** Modern save services provide contextual cues for player conflict resolution.
**Mechanism:** Players cannot safely choose between opaque blobs or timestamps when one contains materially different progress.
**Generalized Principle:** Conflict resolution should expose meaningful progression deltas.
**Transfer:** Show location/chapter, playtime, level, key unlocks, currency, timestamp, and device rather than `save1.json` vs `cloud2`.
**Playtest Question:** Can a player choose correctly without knowing implementation details?

### 8. Save identity is distinct from save content
**Observation:** Platform saves are associated with user/account/device contexts; deleting or selecting the wrong identity can make valid data appear missing.
**Mechanism:** Correct bytes under the wrong owner/slot/world identity are operationally inaccessible or unsafe to merge.
**Generalized Principle:** Persist and validate owner, slot/world ID, content version, and save UUID separately from mutable gameplay state.
**Transfer:** Import should reject or explicitly rebind mismatched identities rather than silently accepting them.
**Playtest Question:** What happens if a valid save is imported into the wrong profile or world slot?

### 9. Autosave needs a recovery horizon
**Observation:** Frequent autosave improves convenience but can rapidly propagate a bad state through every recent copy.
**Mechanism:** Backup frequency without generational diversity can duplicate corruption rather than protect against it.
**Generalized Principle:** Backup policy should preserve time-separated recovery points, not merely the last N writes.
**Transfer:** Keep recent dense generations plus sparse older checkpoints (for example session-start/milestone backups).
**Playtest Question:** How far back can the player recover after corruption goes unnoticed for several saves?

### 10. Migration and gameplay updates should not share an irreversible step
**Observation:** Loading an old save may trigger schema conversion and then immediate autosave.
**Mechanism:** If migration has a subtle defect, immediate overwrite can destroy the pre-migration evidence and fallback.
**Generalized Principle:** Preserve the original generation until the migrated state has survived validation and at least one safe commit boundary.
**Transfer:** Mark migrated saves as candidate state; retain the source version until successful load/play/save completes.
**Playtest Question:** Can QA roll back after discovering a migration bug one session later?

### 11. Unknown future versions must fail safely
**Observation:** Versioned save systems need explicit behavior for unknown versions; older builds may encounter newer saves after rollback or device mismatch.
**Mechanism:** Guessing at a future schema can reinterpret data incorrectly and then overwrite it.
**Generalized Principle:** Never destructively load a schema newer than the code understands.
**Transfer:** Enter read-only/error recovery path, preserve bytes, identify required game version, and avoid autosave.
**Playtest Question:** What happens when an older build sees a save created by a newer build?

### 12. Export/import is part of resilience, not only a power-user feature
**Observation:** Cloud and platform recovery can be unavailable, delayed, account-bound, or conflict-prone.
**Mechanism:** A portable snapshot creates an independent recovery domain.
**Generalized Principle:** Where platform rules allow it, provide verifiable export/import with version and integrity metadata.
**Transfer:** Puzzle RPG and other web games can export JSON containing schema version, save UUID, revision, timestamp, checksum and game build metadata.
**Playtest Question:** Can an exported save be validated before it replaces any local state?

### 13. Recovery success must be observable
**Observation:** Recovery systems need to distinguish active save, recovered backup, migration result, and failure reason.
**Mechanism:** Silent fallback can hide data loss and make later bug reports impossible to diagnose.
**Generalized Principle:** Recovery is a state transition that deserves explicit telemetry/logging and restrained player messaging.
**Transfer:** Record recovery source generation, reason, migration chain, validation result, and resulting revision without storing unnecessary personal data.
**Playtest Question:** After an automatic recovery, can support/QA determine exactly what happened?

### 14. Save tests need destructive fault injection
**Observation:** Ordinary happy-path save/load tests do not exercise interrupted writes, truncation, stale cloud state, or bad migrations.
**Mechanism:** Reliability failures occur between nominal states.
**Generalized Principle:** Test save systems by deliberately breaking transaction boundaries and historical inputs.
**Transfer:** CI matrix: truncate candidate, corrupt checksum, kill between stage/commit, load every old fixture, duplicate revision, future version, divergent offline branches.
**Playtest Question:** Which injected fault can still erase all recoverable progress?

## Promotions

Strong enough for cross-project promotion:
- Save schemas are long-lived compatibility contracts.
- Saving should be transactional: candidate → validation → commit, preserving known-good state.
- Parse validity and gameplay-state validity are separate checks.
- Cloud sync must resolve competing histories rather than blindly copy the newest file.
- Recovery must preserve evidence and avoid destructive action until a valid source is chosen.
- Historical save fixtures and fault injection belong in CI.

## Immediate project transfer

### Puzzle RPG
- version every exported/local save
- sequential migration registry
- keep active + previous + milestone generation
- validate import before replacing localStorage
- include save UUID/revision/build metadata in JSON export

### Procedural / long-run games
- save generator/content version separately from save schema version
- validate seed and world identity before loading generated state

### All iPhone/PWA projects
- treat browser storage writes as fallible
- avoid a single-key overwrite as the only persistence path for valuable progression
- expose export/import where appropriate
