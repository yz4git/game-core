## New observations

### 1. Ping is an eligibility input before it is a ranking input
**Observation:** Production matchmakers distinguish hard compatibility filters from weighted ranking among already-valid candidates.

**Mechanism:** A hard network threshold prevents candidates whose common region cannot meet the experience floor; a softer distance/weight then prefers better candidates inside the valid set.

**Generalized Principle:** Separate **playability gates** from **quality preferences**. Never let a high skill-match score compensate for a connection that violates the mode's minimum playable envelope.

**Transfer:** Ranked fighting can reject excessive RTT/jitter while casual co-op may admit it but rank it lower.

**Playtest Question:** Can the matchmaker ever choose a numerically attractive skill match that the game simulation cannot present fairly?

### 2. A match needs a common feasible region, not individually good pings
**Observation:** Region-selection systems evaluate whether the group shares an acceptable server/relay region.

**Mechanism:** Each ticket contributes measurements to candidate regions; the match is viable only where all required members remain inside policy.

**Generalized Principle:** Optimize the **group's feasible intersection**, not each player's individually best data center.

**Transfer:** For parties, show when one member collapses the common-region set instead of silently giving everyone a bad server.

**Playtest Question:** Does the chosen region minimize one player's ping while making another cross the fairness boundary?

### 3. Network quality is multidimensional
**Observation:** Current QoS allocation considers more than latency; packet loss can materially alter quality even at similar RTT.

**Mechanism:** Two paths with equal median ping can differ in burst loss, jitter and effective update cadence.

**Generalized Principle:** Do not reduce connection quality to a single ping number.

**Transfer:** Build a network suitability vector such as RTT p50/p95, jitter p95, loss, burst-loss length and route stability, then derive mode-specific gates.

**Playtest Question:** Do two users with the same displayed ping experience meaningfully different rollback/correction rates?

### 4. Queue relaxation is a design curve, not a timeout switch
**Observation:** Matchmaking systems support staged, time-based expansion of constraints.

**Mechanism:** Search starts narrow and broadens as wait cost rises.

**Generalized Principle:** Define a **quality-loss curve over wait time** rather than one abrupt `good match → anything` transition.

**Transfer:** Example policy: preserve network floor, slowly widen skill first, then region preference, while never relaxing protocol/trust incompatibility.

**Playtest Question:** At each wait-time band, is the newly admitted quality loss preferable to another interval of waiting?

### 5. Not every rule should relax
**Observation:** Production systems allow some rules to become optional while hard rejection rules remain absolute.

**Mechanism:** Relaxable preferences and invariant compatibility constraints occupy different layers.

**Generalized Principle:** Classify queue rules as `INVARIANT`, `FLOOR`, `RELAXABLE`, or `PREFERENCE`.

**Transfer:** Build/protocol mismatch is invariant; severe network unplayability is a floor; skill spread may be relaxable; map preference is usually preference.

**Playtest Question:** Is any rule currently becoming optional merely because the player waited, even though violating it breaks correctness or fairness?

### 6. Relax the dimension that harms the genre least
**Observation:** Rule weighting exists because skill, geography, shared content and other qualities do not have equal experiential value.

**Mechanism:** Candidate distance can combine several dimensions with different weights while hard filters remain intact.

**Generalized Principle:** Queue expansion order should be **genre-specific**.

**Transfer:** Fighting: protect network timing strongly. Social co-op: protect party/content compatibility and tolerate more skill spread. Racing: protect update stability and lobby population while allowing wider rating spread in low population.

**Playtest Question:** When the queue broadens, which player-visible quality degrades first?

### 7. Party quality should be measured at the worst relevant edge
**Observation:** Group formation requires all members to share viable infrastructure, not merely a good average.

**Mechanism:** An average can hide one member beyond the playable threshold.

**Generalized Principle:** For hard playability, use worst-member or percentile constraints rather than only group means.

**Transfer:** Record max RTT to selected region, worst loss band and party spread alongside averages.

**Playtest Question:** Can a four-player party pass because three excellent links numerically hide one unusable link?

### 8. Queue health changes the correct policy
**Observation:** Matchmaking systems broaden constraints as wait grows, and large queues can be partitioned while smaller populations need wider candidate pools.

**Mechanism:** Population density determines whether strict segmentation improves quality or creates starvation.

**Generalized Principle:** Matchmaking policy needs **population-aware observability**, even if the rules themselves remain deterministic.

**Transfer:** Track eligible-candidate count per expansion stage and region rather than tuning solely from aggregate wait time.

**Playtest Question:** Is a quality problem caused by bad thresholds, or simply by a queue segment with too few compatible candidates?

### 9. Queue partitioning can create invisible starvation
**Observation:** Pools/queues deliberately separate tickets by mode, platform, region or attributes.

**Mechanism:** Every partition improves specificity but reduces candidate density.

**Generalized Principle:** Treat every new queue dimension as a **population tax**.

**Transfer:** Before adding a dedicated touch/controller/ranked/region pool, estimate concurrent compatible population and fallback path.

**Playtest Question:** Which segmentation rule contributes the most wait time for the least measurable match-quality gain?

### 10. QoS must be fresh enough to describe the upcoming match
**Observation:** Modern services measure QoS at runtime and attach it to matchmaking/allocation decisions.

**Mechanism:** Network routes change; old measurements can select a region that is no longer good.

**Generalized Principle:** Give network measurements an age and confidence horizon.

**Transfer:** Ticket schema should include measurement timestamp and test cohort; stale QoS triggers remeasurement or lower confidence rather than silent reuse.

**Playtest Question:** How old can a measurement become before its selected-region prediction noticeably degrades?

### 11. Matchmaking quality must be evaluated after the match starts
**Observation:** A queue can satisfy its configured rules yet the real session may still exhibit rollback, loss or disconnect problems.

**Mechanism:** Pre-match probes are predictions of in-match quality, not ground truth.

**Generalized Principle:** Close the loop from **ticket prediction → allocated route → actual match telemetry → outcome/quit sentiment**.

**Transfer:** Join matchmaking ticket ID, selected region, pre-match QoS, in-match RTT/jitter/loss/rollback and early-leave reason in analysis.

**Playtest Question:** Which pre-match metric best predicts correction rate, disconnects and negative rematch behavior?

### 12. Thresholds need false-accept and false-reject analysis
**Observation:** Tight thresholds improve admitted quality but reject candidates who may have played acceptably; loose thresholds do the reverse.

**Mechanism:** A threshold is a classifier with two error types.

**Generalized Principle:** Calibrate network gates from outcome distributions, not intuition or a universal ping folklore number.

**Transfer:** For each proposed threshold, measure bad-match admission rate, good-match rejection rate and added queue time.

**Playtest Question:** What quality improvement does the threshold buy per second of added median/p95 wait?

### 13. Mode stakes should change the admissible network envelope
**Observation:** The same service can support queues with different rules and priorities.

**Mechanism:** A correction tolerated in casual play may be unacceptable when rank, tournament progression or scarce rewards are at stake.

**Generalized Principle:** Network eligibility is a **mode policy**, not a global constant.

**Transfer:** Ranked/tournament modes can require stronger network and trust floors; casual/custom rooms can expose looser choices explicitly.

**Playtest Question:** Are high-stakes outcomes being awarded under a connection envelope originally tuned for casual availability?

### 14. Explain degraded matchmaking without exposing exploitable internals
**Observation:** Long waits and relaxed rules change the quality players receive, but opaque outcomes feel arbitrary.

**Mechanism:** A small amount of truthful state—search widening, alternate region, estimated quality band—can set expectations without revealing exact anti-abuse thresholds.

**Generalized Principle:** Communicate **quality class and trade-off**, not necessarily exact enforcement internals.

**Transfer:** UI can say `Expanding skill range` or `Searching wider regions` and allow opt-out for strict-quality users.

**Playtest Question:** After a poor match, can the player understand whether they chose a wider search or the system unexpectedly failed its promise?

## Implementation-ready model

### Ticket telemetry
Store at minimum:
- queue/mode/ruleset/build/protocol
- party ID + party size
- QoS measurement timestamp
- candidate-region RTT p50/p95
- jitter p95
- packet loss + burst-loss band
- input/device/platform compatibility attributes where relevant
- expansion stage / wait age

### Rule classes
1. `INVARIANT`: build/protocol/content/trust compatibility
2. `FLOOR`: mode-specific minimum network playability
3. `RELAXABLE`: skill spread, secondary geography constraints, party composition where safe
4. `PREFERENCE`: map/language/cosmetic/social preferences

### Quality loop
`MEASURE → FILTER COMMON FEASIBLE REGIONS → HARD GATES → RANK VALID CANDIDATES → TIME-BASED EXPANSION → ALLOCATE → OBSERVE REAL MATCH → CALIBRATE`

### Calibration metrics
- matchmaking wait p50/p95/p99
- eligible candidates per stage
- no-match / give-up rate
- selected-region distribution
- pre-match QoS vs in-match RTT/jitter/loss error
- rollback depth/frequency or correction magnitude
- disconnect / reconnect rate
- first-120-second quit rate
- rematch / continue rate
- skill imbalance outcome metric
- false-accept / false-reject rate for each proposed network floor

## Practical genre starting hypotheses (not universal constants)

Do not hard-code universal ping thresholds from this note. Derive them from each game's simulation and player outcomes.

- rollback fighting: preserve timing/correction envelope before skill perfection
- racing: prioritize route stability, common region and correction safety; widen rating before accepting unstable paths
- co-op action: protect party continuity and correctness, tolerate broader skill
- turn-based / asynchronous: latency floor can be much looser; focus on disconnect/recovery and protocol compatibility
- ranked/high-stakes: stricter network + trust provenance than casual/custom

## Promotion candidates

Cross-source principles suitable for core/playtest promotion:
- playability gates and quality preferences must be separate
- queue relaxation is a deliberate quality-loss curve
- every queue partition is a population tax
- threshold tuning requires false-accept/false-reject analysis against actual match outcomes
- matchmaking telemetry must close the loop from pre-match QoS to in-match experience
