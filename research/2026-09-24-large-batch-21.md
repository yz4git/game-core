## Observations → Mechanisms → Generalized Principles → Transfer → Playtest Questions

### 1. Replay retention is a compatibility policy
**Observation:** Overwatch retained recent match replays only for the current patch, resetting them when a new patch shipped.
**Mechanism:** Simulation/content changes make old interactive replay state expensive or unsafe to interpret under new code.
**Generalized Principle:** Replay lifetime should be explicitly tied to compatibility guarantees rather than treated as unlimited history.
**Transfer:** Store replay format/build/content versions and choose same-version, migration, metadata-only, or rendered-video fallback policies.
**Playtest Question:** What exactly happens when a user opens a replay created before a balance/content patch?

### 2. A bounded recent-history window can be a product feature
**Observation:** Overwatch exposed a small recent-match list rather than an unlimited archive.
**Mechanism:** Bounded retention reduces storage/indexing burden and keeps the replay browser relevant to current learning.
**Generalized Principle:** Retention should match the replay's job: immediate learning, evidence, sharing, or long-term archival.
**Transfer:** Keep recent interactive replays locally; promote explicitly saved/bookmarked runs into longer-lived storage.
**Playtest Question:** Can users reliably save the one replay they care about before automatic eviction?

### 3. Replay is more useful when perspective is mutable
**Observation:** Blizzard replay viewers expose first-person, third-person, overhead/free cameras and player switching.
**Mechanism:** Different questions require different information projections: execution, positioning, rotations, objective flow.
**Generalized Principle:** Replay should expose multiple explanatory views rather than merely reproduce the original camera.
**Transfer:** Racing: cockpit + chase + track overview; fighting: player + neutral side + hitbox/debug view; strategy: unit + tactical overview.
**Playtest Question:** Can a player answer both “what did I press?” and “why was I in the wrong place?” from one replay tool?

### 4. Time control converts replay into an analysis instrument
**Observation:** Replay viewers support pause and variable playback speed.
**Mechanism:** Slowing critical transitions expands a sub-second decision into an inspectable sequence; speeding quiet intervals reduces review cost.
**Generalized Principle:** Analysis value depends on temporal navigation as much as recording fidelity.
**Transfer:** Add frame/step, event jump, speed controls, and bookmarks before adding decorative replay effects.
**Playtest Question:** How many interactions are needed to reach and inspect the decisive moment?

### 5. Tactical overlays should explain relationships, not duplicate HUD
**Observation:** Overwatch replay guidance uses map overlays and status indicators to understand team-fight development and rotations.
**Mechanism:** A global view exposes spatial relations hidden from a single player's camera.
**Generalized Principle:** Replay overlays should reveal causal structure unavailable during live play.
**Transfer:** Show route divergence, aggro, resource state, target selection, line-of-sight, objective pressure, or split deltas where useful.
**Playtest Question:** Does the replay overlay answer a question the normal HUD could not answer?

### 6. Spectator and player clients are different trust roles
**Observation:** Server-authoritative systems distinguish active participants from spectators; spectator clients need not send gameplay commands.
**Mechanism:** Separating roles reduces authority surface and clarifies bandwidth/state requirements.
**Generalized Principle:** Spectator capability should be least-authority by default.
**Transfer:** Issue read-only spectator/session tokens and reject gameplay command paths for observers.
**Playtest Question:** Can a spectator connection influence authoritative match state through any normal code path?

### 7. Large audiences should not scale directly against the match server
**Observation:** Public networking guidance notes that distributing one reliable snapshot/replay stream through a replicator avoids multiplying CPU/bandwidth load on the authoritative game server.
**Mechanism:** Fan-out is moved away from latency-critical simulation.
**Generalized Principle:** Spectator distribution architecture should decouple audience size from match-authority cost.
**Transfer:** Record authoritative event/snapshot stream once; serve replay/spectator consumers from separate distribution infrastructure when scale warrants it.
**Playtest Question:** Does adding spectators measurably alter simulation latency or player packet delivery?

### 8. Replay can serve learning, validation and entertainment from one event stream
**Observation:** The same replay state supports strategy study, professional observation, highlights and match review.
**Mechanism:** A sufficiently structured event/state record can be projected into different interfaces.
**Generalized Principle:** Prefer one trustworthy replay substrate with purpose-specific views over independent ad-hoc recording systems.
**Transfer:** QA viewer adds checksums/debug state; player viewer hides private/debug data; spectator viewer adds camera/overlay controls.
**Playtest Question:** Are multiple replay products disagreeing because they record separate truths?

### 9. Bookmarking is a first-class compression of human attention
**Observation:** Observer tools allow saved camera positions and rapid return to useful views.
**Mechanism:** Users encode “this perspective/location matters” so repeated analysis avoids navigation overhead.
**Generalized Principle:** Replay UX should let users persist attention anchors, not only raw time positions.
**Transfer:** Bookmark timestamp + camera + tracked entity + overlay state + optional note.
**Playtest Question:** Can a reviewer compare the same encounter location across multiple runs quickly?

### 10. Replay sharing needs metadata minimization
**Observation:** A replay can contain much more state than a rendered clip: player identifiers, chat-like events, precise timing, hidden state, debug data or session identifiers.
**Mechanism:** Sharing the raw artifact can expose information unnecessary for the viewer's purpose.
**Generalized Principle:** Treat replay export as a privacy boundary; share the minimum state needed for the selected use.
**Transfer:** Separate public display names from account IDs; strip auth/session/debug/private-team fields; offer clip/rendered export where raw state is unnecessary.
**Playtest Question:** What information can a recipient extract from the replay file that is not visible in the replay UI?

### 11. Server authority and replay authority should align
**Observation:** Modern competitive networking commonly uses server-authoritative state with client prediction.
**Mechanism:** Recording client presentation as truth can preserve predicted/corrected artifacts rather than adjudicated outcomes.
**Generalized Principle:** Competitive validation replay should originate from or be verifiable against authoritative state.
**Transfer:** Store authoritative events/checkpoints plus client presentation metadata only when needed for diagnosis.
**Playtest Question:** Can a disputed result be reconstructed without trusting the claimant's client state?

### 12. Spectator analytics should measure comprehension, not only audience size
**Observation:** Observer tools deliberately provide player switching, tactical views and temporal control to help viewers understand action.
**Mechanism:** View-switching and rewind behavior reveal where the live presentation failed to communicate state or where interest concentrates.
**Generalized Principle:** Spectator telemetry should include comprehension proxies, not only concurrent viewers/watch time.
**Transfer:** Aggregate camera switches, rewind points, event jumps, overlay use and exits without retaining unnecessary identity.
**Playtest Question:** Which moments repeatedly trigger rewinds or camera changes, and are they exciting or confusing?

### 13. Interactive replay and archival media have different longevity
**Observation:** Patch-bound interactive replays may expire while conventional video remains viewable independent of simulation code.
**Mechanism:** Interactive state depends on executable semantics; rendered media depends primarily on codecs/container support.
**Generalized Principle:** Preserve long-term cultural/competitive moments in a representation less coupled to live simulation.
**Transfer:** For records/tournaments, retain metadata + validated result + optional rendered highlight/video even after interactive replay expiry.
**Playtest Question:** What evidence remains after the executable replay format is no longer supported?

### 14. Replay browsing needs explicit identity and provenance
**Observation:** A replay library can mix patches, modes, maps, players, tournaments and locally saved runs.
**Mechanism:** Without provenance, users can compare incompatible runs or misattribute results.
**Generalized Principle:** Replay metadata is part of correctness, not decoration.
**Transfer:** Include match/run ID, build/protocol, map/content version, mode/ruleset, seed where relevant, authority source, created time and retention class.
**Playtest Question:** Can two visually similar but rules-incompatible replays be mistaken for a fair comparison?

## Promotions

Strong enough for cross-project promotion:
- Replay lifetime must follow an explicit compatibility/retention policy.
- Competitive replay truth should align with authoritative simulation.
- Spectators should be read-only/least-authority clients.
- Audience fan-out should not scale directly on the match server.
- Replay export is a privacy boundary and should minimize metadata/state.
- Spectator analytics should measure comprehension behavior as well as audience size.

## Implementation-ready replay manifest

Recommended minimum manifest:
- replayFormatVersion
- gameBuild
- protocolVersion
- content/map version
- mode/ruleset
- match/run ID
- authority source
- creation timestamp
- retention class / expiry
- participants as public replay identities, not auth credentials
- seed / generator version when applicable
- integrity hash
- optional parent/bookmark/highlight references

Never place passwords, auth tokens, raw session cookies, or unnecessary private account identifiers in replay artifacts.

## Production QA

Automate:
- patch N replay opened on patch N+1 according to declared policy
- expiry/eviction with pinned replay preservation
- spectator read-only command rejection
- 1 / 10 / 100 / 1000 spectator fan-out load model where relevant
- privacy scan of exported replay manifest/payload
- authoritative result versus replay reconstruction checksum
- seek/bookmark correctness
- replay browser filtering by incompatible version/ruleset
