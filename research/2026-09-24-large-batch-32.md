## New observations

### 1. Prediction should predict experience, not grant truth
**Observation** — Low-latency local response and authoritative validation solve different problems.
**Mechanism** — The client immediately simulates likely movement/actions while the authority later accepts, clamps or rejects the underlying input/result.
**Generalized Principle** — A prediction path must never silently become a permission path.
**Transfer** — Movement, attacks, cooldown previews, inventory UI and interaction prompts can feel immediate while score, damage, rewards and ownership remain authoritative.
**Playtest Question** — Which locally immediate actions can currently create irreversible shared state before authority accepts them?

### 2. Send player intent when the server can reconstruct the result
**Observation** — A client claim such as “I am at X” or “I dealt 80 damage” contains more authority than an input such as “move right” or “fire now.”
**Mechanism** — The server re-simulates or validates bounded intent against canonical state.
**Generalized Principle** — Prefer the least-authoritative message that still expresses the player decision.
**Transfer** — Send input sequence, aim/timestamp and action ID; derive movement, cooldown, hit and reward where practical.
**Playtest Question** — Can a modified client submit a plausible-looking result that the server cannot independently derive or bound?

### 3. Validation must be temporal, not only spatial
**Observation** — Position/range checks alone miss speed hacks, impossible action rates and reordered old commands.
**Mechanism** — Authority validates input sequence, authoritative tick/window, cooldown/resource history and maximum state transition per interval.
**Generalized Principle** — Every competitive state transition has a time budget as well as a value/range budget.
**Transfer** — Movement delta, fire cadence, dodge invulnerability, resource gain and interaction frequency all need temporal invariants.
**Playtest Question** — What impossible action becomes legal if packets are individually valid but submitted too quickly or out of order?

### 4. Lag compensation is bounded historical permission
**Observation** — Rewinding hitboxes improves WYSIWYG for honest latency but also expands the historical states against which an action may be accepted.
**Mechanism** — The authority retains a finite history and validates a claimed action time inside a bounded rewind window.
**Generalized Principle** — Compensation windows are security/fairness budgets, not merely feel parameters.
**Transfer** — Cap rewind age; clamp client timestamps; reject future/too-old claims; log accepted rewind depth by player and weapon/action class.
**Playtest Question** — At the maximum accepted rewind, does the attacker gain a repeatable advantage that a low-latency defender cannot understand?

### 5. Reconciliation needs identity, not just values
**Observation** — Re-sent or replayed commands can look individually legal.
**Mechanism** — Monotonic input/action sequence IDs and authoritative acknowledgement distinguish new intent from duplicate/stale intent.
**Generalized Principle** — Irreversible network actions need stable identity and idempotent handling.
**Transfer** — Purchase, pickup, unique reward, hit event and ownership request should not execute twice after retry/reconnect.
**Playtest Question** — Can duplicated, delayed or reconnect-replayed packets duplicate any irreversible outcome?

### 6. Ownership and authority are separate capabilities
**Observation** — A player may be the logical owner of an object without being allowed to dictate every gameplay property of it.
**Mechanism** — Ownership controls who may request/drive interaction; authority controls whose state is canonical.
**Generalized Principle** — Do not collapse “belongs to this player,” “may send input for it,” and “may define truth for it” into one flag.
**Transfer** — Vehicles, grabbed physics objects, summons, projectiles and build pieces can use distinct ownership/input/state permissions.
**Playtest Question** — If a client gains ownership, which fields become writable, and are any of those stronger than required?

### 7. Authority transfer needs a monotonic generation
**Observation** — A stale former owner/host can later deliver valid-shaped state.
**Mechanism** — Authority/ownership sequence or epoch increments when control changes; older generations lose conflicts even if packets arrive later.
**Generalized Principle** — Authority is versioned state.
**Transfer** — Per-object authority sequence complements the match-level authority epoch introduced in Batch 31.
**Playtest Question** — After transfer plus packet delay, can an old authority regain control without a new grant?

### 8. Shared/client authority changes the threat model, not just latency
**Observation** — Client-authoritative/shared topologies reduce latency/cost but cannot offer the same integrity guarantees as a dedicated authoritative simulation.
**Mechanism** — The machine benefiting from an outcome may also be able to manufacture the state supporting it.
**Generalized Principle** — Topology is part of competitive rules and trust classification.
**Transfer** — Casual co-op may tolerate relayed/client authority; ranked ladders, scarce rewards and public records should raise authority requirements or independently validate results.
**Playtest Question** — Are rewards/rankings stronger than the trust model of the match that produces them?

### 9. Host authority has an asymmetric trust hole
**Observation** — A listen host can validate guests while remaining able to modify its own authoritative process.
**Mechanism** — Host topology centralizes truth on a participant-controlled machine.
**Generalized Principle** — “Server authoritative” is insufficient wording; specify who controls the server process.
**Transfer** — Mark dedicated / trusted service / listen-host / shared / relayed sessions in telemetry and eligibility rules.
**Playtest Question** — Can a listen-host result enter the same competitive record pool as a trusted-server result without provenance?

### 10. Correct locally, adjudicate authoritatively, smooth visually
**Observation** — Hard corrections expose authority but can make honest players feel punished by network variance.
**Mechanism** — Canonical state snaps/re-simulates immediately while presentation eases small discrepancies without feeding them back into simulation.
**Generalized Principle** — Cheat resistance and good feel are not opposites if simulation truth and presentation are separated.
**Transfer** — Preserve exact collision/state correction while smoothing camera/mesh/animation offsets inside strict visual limits.
**Playtest Question** — Can visual smoothing hide a correction so long that the displayed affordance becomes false?

### 11. Security telemetry should measure impossible transitions, not opaque suspicion
**Observation** — Raw “cheat score” is hard to debug and can confuse network faults with malicious behavior.
**Mechanism** — Record concrete invariant violations: timestamp clamp, speed envelope breach, cooldown violation, duplicate action, stale authority generation, impossible resource delta, excessive rewind request.
**Generalized Principle** — Detection telemetry should be explainable in gameplay terms.
**Transfer** — Aggregate per match/device/network condition before enforcement; preserve short repro traces around severe violations.
**Playtest Question** — Can QA reproduce why a session was flagged from the stored invariant events alone?

### 12. False-positive testing belongs in the network fault matrix
**Observation** — Burst loss, jitter, reordering, suspend/resume and host migration can resemble manipulation.
**Mechanism** — Security rules run against intentionally hostile network traces with honest clients.
**Generalized Principle** — An anti-cheat invariant is incomplete until tested against legitimate transport disorder.
**Transfer** — Combine Batch 19/27/31 fault traces with validation assertions and measure false reject/correction rates.
**Playtest Question** — Which honest fault trace produces the highest security violation count, and why?

### 13. Reward authority can be stricter than movement authority
**Observation** — Not every subsystem needs the same trust/latency trade-off.
**Mechanism** — Fast movement may use prediction or temporary object authority while durable progression waits for trusted validation.
**Generalized Principle** — Define authority per consequence class, not only per game mode.
**Transfer** — Cosmetic local motion < match score < ranked result < scarce economy/unique grant can form increasing trust tiers.
**Playtest Question** — What is the most valuable durable outcome a low-trust client can currently create directly?

### 14. Information authority matters alongside state authority
**Observation** — A client can obey all write rules yet cheat if it receives hidden state it should never know.
**Mechanism** — Wall-hacks/information exploits consume replicated data rather than falsifying outbound state.
**Generalized Principle** — Authoritative writes do not protect secrets; replication visibility must follow least privilege.
**Transfer** — Interest management, fog-of-war projection and spectator field allowlists should prevent unnecessary enemy/private state from reaching the client.
**Playtest Question** — If the client were fully inspected, what hidden opponent/future/private information could it reveal?

## Implementation-ready trust matrix

For every replicated/action domain, record:

`domain | client may predict | client may request | client may author | authority validator | temporal bound | idempotency key | visibility class | durable consequence`

Minimum domains: locomotion, aim, fire, hit, damage, pickup, object ownership, score, match result, currency, unique reward, inventory, hidden opponent state.

Recommended validation pipeline:

`INPUT/REQUEST → ID+EPOCH CHECK → TEMPORAL WINDOW → STATE/RULE INVARIANTS → AUTHORITATIVE APPLY → ACK → CLIENT RECONCILE → PRESENTATION SMOOTH`

Never make a retry bypass an earlier gate.

## Telemetry / QA additions

Track distributions rather than only totals:
- prediction correction magnitude and frequency
- rejected/stale input sequence count
- timestamp clamp and rewind depth
- movement/action-rate envelope violations
- duplicate/idempotency suppression
- stale authority epoch/ownership generation
- reward/result provenance by topology
- false rejects under scripted jitter/loss/reorder/background/migration traces
- hidden-state bytes replicated per visibility class

Fault-injection cases:
1. duplicate every irreversible request
2. reorder valid inputs across cooldown boundary
3. future timestamp and just-inside/just-outside rewind timestamps
4. speed envelope edge under jitter
5. ownership transfer with late former-owner state
6. listen-host result submission into ranked pipeline
7. reconnect replay of already-acknowledged reward
8. background/resume with stale input queue
9. host migration during pending hit/reward
10. inspect client replication for hidden opponent/private state

## Promotion candidates

Promote cross-system principles:
- prediction is provisional experience, not authority
- validate intent with temporal/state invariants
- irreversible actions require identity/idempotency
- authority and ownership are separate, versioned capabilities
- topology determines trust eligibility
- durable rewards may require stronger authority than moment-to-moment feel
- state authority does not solve hidden-information leakage
- anti-cheat rules require false-positive testing under real network faults
