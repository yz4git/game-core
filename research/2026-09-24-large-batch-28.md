## Observation → Mechanism → Generalized Principle → Transfer → Playtest Question

### 1. Quota is runtime state, not a platform constant
**Observation:** Browser storage limits vary by browser context, device disk, policy, engagement and version; the Storage API exposes estimates rather than a fixed guaranteed number.
**Mechanism:** The browser owns allocation policy and can change the effective budget independently of the game's save schema.
**Generalized Principle:** Never encode a hardcoded storage-capacity assumption into save correctness.
**Transfer:** Before large checkpoints, replay caches, downloaded content or snapshot rotation, inspect estimated usage/quota and retain headroom.
**Playtest Question:** Does saving remain safe when the effective quota is much smaller than the developer's test device?

### 2. Estimated free space is a warning signal, not permission to fill it
**Observation:** `navigator.storage.estimate()` deliberately reports approximate values.
**Mechanism:** Compression, deduplication and privacy protections make the estimate non-exact.
**Generalized Principle:** Storage planning needs a safety margin; `quota - usage` is not a byte-exact write allowance.
**Transfer:** Trigger cleanup/warnings well before 100% estimated utilization.
**Playtest Question:** What happens when the estimate says space remains but the next transaction still fails?

### 3. Quota failure must be a normal tested branch
**Observation:** IndexedDB/Cache/OPFS writes can fail with `QuotaExceededError`.
**Mechanism:** Capacity pressure converts an otherwise valid save operation into an expected runtime failure.
**Generalized Principle:** Out-of-space is part of the save state machine, not an exceptional crash-only path.
**Transfer:** Catch quota failure, preserve the known-good generation, prune only disposable data, retry once if safe, then surface recovery UI.
**Playtest Question:** Can a full device destroy the only good save or falsely report success?

### 4. Transaction success is the commit boundary
**Observation:** IndexedDB exposes transaction `complete` and `abort`; the specification requires committed transaction changes to be atomic.
**Mechanism:** Individual request success is earlier than transaction completion, while abort can result from quota, I/O or handler failures.
**Generalized Principle:** UI must not announce SAVE COMPLETE until the storage transaction itself commits.
**Transfer:** Advance active-save pointers and show success feedback only from transaction completion.
**Playtest Question:** If the transaction aborts after an individual write request succeeds, does the game still claim the save completed?

### 5. Atomic transaction does not make the whole origin durable
**Observation:** WebKit can evict best-effort origin data under storage pressure; eviction normally happens at origin granularity.
**Mechanism:** A perfectly committed IndexedDB transaction can later disappear because persistence and transaction atomicity solve different failure classes.
**Generalized Principle:** Separate **write atomicity** from **long-term retention** in save design.
**Transfer:** Critical progress should combine transactional local storage with persistence request where appropriate and user-controlled export/cloud backup when available.
**Playtest Question:** Can the game distinguish a corrupt save from an origin whose local data was evicted entirely?

### 6. Persistence is a capability, not an assumption
**Observation:** WebKit supports `persist()` / `persisted()` and excludes persistent origins from normal eviction policy, but granting behavior belongs to the user agent.
**Mechanism:** Applications can request stronger retention but cannot assume it was granted.
**Generalized Principle:** Save UX should know and expose its durability tier without blocking normal play when persistence is unavailable.
**Transfer:** Record `storageDurability = persistent | best-effort | unknown` in diagnostics; encourage export for long campaigns when best-effort remains.
**Playtest Question:** Is a denied persistence request handled as a usable but less durable mode rather than a broken game?

### 7. Save data and disposable caches compete for one origin budget
**Observation:** WebKit quota policy covers IndexedDB, Cache API, Service Worker-related storage and file storage under the site's storage budget.
**Mechanism:** Large asset/replay caches can indirectly cause a critical save write to fail.
**Generalized Principle:** Storage priority must be explicit across subsystems.
**Transfer:** Reserve budget classes: critical save > recovery generations > user-created content > replay/highlight cache > regenerable asset cache.
**Playtest Question:** Can filling a replay or offline-asset cache prevent the next checkpoint?

### 8. Cleanup order is part of data-loss policy
**Observation:** A quota error often invites deletion to free space, but indiscriminate cleanup can remove the very recovery generations needed after a failed save.
**Mechanism:** Capacity recovery chooses which historical information survives.
**Generalized Principle:** Define an eviction ladder before failures occur.
**Transfer:** Delete regenerable caches first, then old non-pinned replays; preserve current/previous known-good, milestone saves and explicit exports.
**Playtest Question:** Under forced quota pressure, which exact records are removed first and can QA verify the order?

### 9. Origin-wide eviction should look like first-run-with-recovery, not corruption
**Observation:** WebKit can delete an origin's data as a unit under applicable eviction conditions.
**Mechanism:** On next launch, multiple stores may all be absent simultaneously.
**Generalized Principle:** Missing-all-local-state is a distinct diagnostic condition from one malformed save record.
**Transfer:** Detect empty database + prior account/cloud/export evidence and offer recovery rather than silently creating a new campaign over the missing identity.
**Playtest Question:** After simulated origin eviction, does startup make irreversible new-state writes before checking recovery sources?

### 10. Browser context changes durability assumptions
**Observation:** WebKit distinguishes browser apps, embedded web content and Home Screen web apps in storage policy; private browsing also has different retention behavior.
**Mechanism:** The same game URL can run under materially different storage conditions.
**Generalized Principle:** Save guarantees belong to the runtime context, not just the URL or build.
**Transfer:** Include context/capability checks in diagnostics and test Safari tab, installed Home Screen PWA and private browsing separately.
**Playtest Question:** Does the same campaign behave predictably across tab/PWA/private contexts?

### 11. Headroom should be reserved for the next critical transaction
**Observation:** A game can be below quota yet lack enough room for candidate + previous generation + migration working copy.
**Mechanism:** Transactional save resilience temporarily needs more storage than the final compact save size.
**Generalized Principle:** Budget for peak transactional footprint, not steady-state save size.
**Transfer:** Maintain `criticalReserve >= max(candidate + validation metadata + recovery delta)` and prune disposable data before crossing it.
**Playtest Question:** Can a migration fail because there is room for the final save but not both old and new generations simultaneously?

### 12. Quota tests must inject failure at transaction phases
**Observation:** Save correctness depends on behavior before, during and after transaction commit.
**Mechanism:** A single "disk full" test misses failures around staging, metadata update and cleanup.
**Generalized Principle:** Fault injection should target storage state-machine boundaries.
**Transfer:** Inject quota/I/O failure before candidate write, mid-transaction, before pointer advance, during cleanup and on retry.
**Playtest Question:** At every injected point, is at least one known-good generation still discoverable?

### 13. Storage telemetry should be privacy-minimal and actionable
**Observation:** Capacity debugging needs usage/quota/failure class, not save payload contents.
**Mechanism:** Aggregate storage metadata can explain failures without collecting private gameplay state.
**Generalized Principle:** Diagnose durability with structural metrics before payload logging.
**Transfer:** Log estimated usage/quota ratio, durability tier, save bytes, generations retained, transaction outcome and failure code.
**Playtest Question:** Can support identify quota pressure without receiving the player's raw save?

### 14. Long campaigns need a user-owned escape hatch
**Observation:** Local browser storage remains subject to browser/device/user lifecycle even when robustly implemented.
**Mechanism:** Device replacement, explicit website-data deletion and some browsing modes sit outside local transactional guarantees.
**Generalized Principle:** Irreplaceable progress should have a portable recovery path.
**Transfer:** Provide validated export/import or account/cloud synchronization for games where loss cost is high; export must preserve schema/version/integrity metadata.
**Playtest Question:** Can a player recover meaningful progress after all local origin storage is intentionally cleared?

## Implementation pattern

Recommended storage tiers:

1. **Critical:** active save identity + current known-good generation
2. **Recovery:** previous known-good + milestone generation
3. **User valuable:** authored levels/builds, pinned replays
4. **Disposable:** generated thumbnails, transient telemetry, unpinned replay cache
5. **Regenerable:** downloaded/generated caches that can be recreated

Pre-save flow:

`estimate → reserve check → prune disposable if needed → stage candidate → validate → IndexedDB transaction → transaction complete → advance known-good metadata → asynchronous optional cleanup`

On `QuotaExceededError`:

`do not destroy known-good → classify pressure → prune disposable → re-estimate → retry bounded once → recovery UI/export guidance`

## QA matrix

- Safari browser tab / Home Screen PWA / private mode where applicable
- low free disk / synthetic quota failure
- candidate larger than normal
- migration temporarily doubles footprint
- replay/cache fills origin before checkpoint
- quota error before and during IndexedDB transaction
- transaction abort after request-level success
- origin data entirely missing on relaunch
- persistence granted / denied / unsupported
- export/import after local deletion
- repeated autosave near reserve threshold

## Promotions

Strong enough for cross-project promotion:
- quota is runtime state, not a constant
- transaction commit and long-term persistence are separate guarantees
- critical save data must outrank caches under storage pressure
- success UI must follow transaction completion
- reserve for peak transactional footprint
- origin-wide loss needs a recovery-aware startup path
- long-lived progress needs a portable escape hatch
