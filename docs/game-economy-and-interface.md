# Game Economy & Interface

RPG・シミュレーションを中心に、通貨・反復操作・移動・因果フィードバックを設計する。

## 1. Money needs competing sinks

通貨が意味を持つのは、欲しいものを全部買えないとき。

競合する支出:
- 成長
- 武器
- 防具
- 消耗品
- 回復
- 情報
- 移動
- 一時強化

「いつでも余る」なら経済は判断を失う。

## 2. Sinks must remain relevant

序盤だけ価値がある店では後半の経済が死ぬ。

後半にも、
- 高価だが便利
- 状況次第で欲しい
- 繰り返し使う
支出を残す。

ただし強制税だけにしない。

## 3. Consumables need timing decisions

消耗品は「持っているだけ」でも「毎戦連打」でも弱い。

- 今使うか
- 次へ残すか
- お金に換えるか
- 別用途へ使うか
の競合を作る。

## 4. Convenience as progression reward

攻略済み区間の反復は、ショートカット・テレポート・帰還で省略できる。

これは難易度低下ではなく、既に証明した作業を減らす報酬になり得る。

## 5. High-frequency UI

一回のメニュー操作は小さくても、総回数で大きな摩擦になる。

優先的に短縮する:
- 回復
- 装備比較
- よく使う魔法
- 地図
- アイテム整理
- セーブ

## 6. Show comparison before commitment

装備変更や購入時に、
- 現在値
- 変更後
- トレードオフ
を比較できるようにする。

試すために旧装備を失うなど、情報不足を罰にしない。

## 7. Simulation causality

設定変更や投資の結果が見えるまで長すぎる場合、中間指標を出す。

例:
- 人流
- 待ち時間
- 満足度
- 交通量
- 在庫
- 予測

結果を完全に即時化する必要はないが、仮説を修正できる材料を返す。

## 8. Save cost

セーブにコストを付けるなら、それが意味あるリスク判断か確認する。

ただの作業税なら、プレイヤーはゲーム外の都合で罰を受ける。

## 9. Playtest questions

- 中盤で所持金の使い道に迷うか
- 終盤に通貨が余っていないか
- 消耗品の使用タイミングに判断があるか
- 100回使うUIは何手必要か
- 装備比較を購入前にできるか
- システム変更の結果を理解できるか
